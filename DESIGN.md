# keel — a float32 BLAS subset in pure Go on `GOEXPERIMENT=simd`

*Design document and Claude Code build plan. Working name "keel" (the foundation member of a hull) — rename at will.*

---

## 1. Mission

A pure-Go, cgo-free float32 BLAS subset whose hot kernels are written against the experimental `simd` / `simd/archsimd` packages (Go 1.26+, `GOEXPERIMENT=simd`). Target: ≥70% of single-threaded OpenBLAS SGEMM on AVX-512 hardware, with kernels that inline, respect safepoints, and parallelize on the caller's `GOMAXPROCS` via goroutines.

**Why it wins if it works:** preemption-safe, GC-friendly, deploys as a normal Go module, composes with the host application's scheduler. cgo-OpenBLAS can match the FLOPS but structurally cannot tell that story.

**Non-goals (v0):** float64 (Gonum owns it), complex types, full BLAS coverage, banded/packed storage, ARM64 (later; the architecture must make it a second microkernel, not a second library), float16 (no element type exists in the simd packages).

## 2. Scope: 15 routines, one keystone

| Level | Routines | Notes |
|---|---|---|
| 1 | `Sdot, Saxpy, Sscal, Snrm2, Sasum, Isamax` | Warm-up; validates shim + test harness |
| 2 | `Sgemv, Sger` | One packing dimension; rehearsal for L3 |
| 3 core | **`Sgemm`** | The keystone. All effort concentrates here |
| 3 derived | `Ssyrk, Strsm, Ssymm` | Blocked-GEMM + small corner kernels (BLIS decomposition) |

Row-major only in the public API (`float32` slices + explicit `ld` strides), matching Go idiom rather than Fortran heritage. Transpose flags supported; the packing routines absorb them for free.

## 3. Architecture

```
keel/
  keel.go              // public API: Sgemm(m,n,k, alpha, a, lda, b, ldb, beta, c, ldc) etc.
  dispatch.go          // runtime feature detect: L1 avx512/avx2/scalar, L3 avx512/scalar (#40)
  internal/vec/        // THE SHIM. All simd/archsimd imports live here and only here.
    vec_avx512.go      //   //go:build goexperiment.simd && amd64
    vec_avx2.go
    vec_scalar.go      //   pure Go; always compiles; the semantic reference
  internal/kern/       // microkernels (straight-line, one intrinsic per op)
    sgemm_16x4_avx512.go
    sgemm_8x6_avx2.go
    sgemm_scalar.go
  internal/pack/       // panel packing (A: MC×KC col-panels; B: KC×NC row-panels)
  internal/block/      // Goto/BLIS loop nest (NC → KC → MC → NR → MR → microkernel)
  internal/oracle/     // float64 reference implementations for every routine
  internal/spill/      // spill-audit tooling (§6)
  bench/               // benchmark harness + optional cgo OpenBLAS reference (dev-only, build-tagged)
```

**The shim is load-bearing.** The simd API broke between 1.26 and 1.27 and will break again before graduation. Every intrinsic keel uses gets one wrapper in `internal/vec` (`Load16`, `Store16`, `FMA`, `Broadcast`, `HSum`, `MaskLoad`…). API churn is absorbed in one directory; kernels never import `simd` directly. The scalar implementation of the shim is the executable spec — every vector op has a scalar twin, and differential tests hold them equal.

## 4. Phases and gates

Every phase ends in an executable gate: a command that exits 0 or 1. No narrative "it works" — the gate script decides. Commit at every green gate.

### Phase 0 — Toolchain probe & shim (≈1 session)
- Install Go 1.27rc (or latest 1.26.x), verify `GOEXPERIMENT=simd go build` with a `//go:build goexperiment.simd` file importing `simd/archsimd` compiles and runs `X86.AVX512()` detection.
- Build `internal/vec` with the ~12 ops SGEMM needs, all three backends.
- **CRITICAL — read, don't recall:** run `go doc simd/archsimd` and read the package source under `$(go env GOROOT)/src/simd/` before writing any wrapper. The API is weeks old, has already had breaking renames, and any remembered function names are presumptively wrong. Copy exact identifiers from `go doc` output into the shim.
- Differential-test every vector op against its scalar twin on random + edge inputs (NaN, ±Inf, denormals, -0).
- **Gate P0:** shim tests pass under all three backends; `FMA` disassembles to **a single fused multiply-add instruction — any `VFMADD*PS` form — rather than a separate multiply and add** (grep `-gcflags=-S` output). If no fused op exists in the current API, stop and surface it: mul+add is a half-of-peak ceiling and changes the target math.
  - **The criterion is fusion, not an encoding** (reworded 2026-08-12, issue #10). This originally named `VFMADD231PS`, which is the form a hand-written K-loop wants and *not* what the compiler emits: go1.26.5 lowers `MulAdd` to `VFMADD213PS`, so the criterion as first written would have failed a toolchain that satisfied it. What P0 needs to establish is that one instruction does the multiply and the add with a single rounding, because that is what sets the achievable ceiling; which of the three operand orders carries it is a separate question with separate consequences, and it belongs where those consequences are — §"Cause of the roofline" below, where 231-vs-213 is the difference between `I = 4.625` and `I ≈ 2.875` and is tracked as a standing task against the lowering. Keeping the two apart means a criterion cannot be satisfied or failed by an encoding change that does not move the ceiling.

### Phase 1 — Level 1 + test harness (≈1 session)
- Implement the six L1 routines on the shim; oracle versions in float64.
- Tolerance model (used everywhere): `|keel − oracle| ≤ C·f(n)·ε₃₂·scale`, with `f(n)=n` for dot-like reductions, `C≈4` slack for FMA/reassociation differences. Encode as one helper; never hand-pick per-test epsilons.
- Property tests: aliasing (`Saxpy(a, x, x)`), zero-length, stride ≠ 1, NaN propagation per BLAS convention.
- **Gate P1:** all L1 tests green on avx512 + scalar; benchmarks show ≥4× scalar for `Sdot` at n=4096.

### Phase 2 — Microkernel + spill audit (THE go/no-go, ≈1–2 sessions)
- Write `sgemm_32x6_avx512.go`. Tile choice: with 16-lane `Float32x16` vectors along M, a 16×4 tile gives only 4 accumulators — too few to hide FMA latency (~4-cycle latency × 2 ports wants ≥8–10 independent chains). Start at **MR=32, NR=6**: 2 vectors along M × 6 columns = **12 accumulators** + 2 A-registers + 1 B-broadcast = 15 live zmm, comfortable for the allocator. If the spill audit stays clean, grow toward MR=32, NR=12 (24 accumulators + 3 = 27 live zmm, near the practical ceiling); grow until spills appear, back off one step, record the frontier in `KERNEL.md`.
- Kernel-shaping rules: pre-slice packed panels to exact length outside the loop (bounds-check elimination — verify with `-gcflags=-d=ssa/check_bce`), pointer-free data (float32 slices ⇒ no write barriers), no function calls inside the K-loop, K-loop unrolled ×4.
- **Spill audit tooling** (`internal/spill`): a small Go program that runs `go build -gcflags=-S` on the kernel package and counts vector stores/loads to stack-relative addresses inside the K-loop body. Also emit `GOSSAFUNC=Kernel32x6 go build` and archive `ssa.html` per commit for human/CC inspection of *why* any spill happened.
- **Gate P2:** `spill-audit` reports **0 accumulator spills** in the steady-state K-loop, AND the raw microkernel (packed inputs, no blocking) clears the **throughput floor defined below**. If either fails after kernel-shaping and one shrink step: STOP, write `docs/spill-report.md` with the ssa.html evidence, and surface the decision (file upstream vs. avo fallback vs. accept AVX2 shapes). Do not silently proceed to Phase 3 on a broken kernel.
- **The throughput floor is roofline-relative on issue-bound hosts** (amended 2026-08-11, ruling on issue #19; supersedes the flat "≥55% of measured peak" for those hosts only). The original criterion has one denominator, the host's measured FMA peak, and so silently assumes the front end can *deliver* the kernel's instruction mix at 55% of that peak. On a host that retires two full-width FMAs per cycle from a ~4-wide front end, it cannot: the instruction budget is `issue_rate ÷ (FMA_rate × insns_per_FMA)` and it caps the achievable fraction *below the floor*, before a single cycle is wasted. Measured on janus.local (i9-9960X): 4.37 insns/cycle ÷ (1.944 FMA/cycle × 4.625 insns/FMA) = **48.6% is the ceiling**, and the kernel measured 46.0% — 94.6% of what the instruction set as-lowered can express (46.1%/94.8% on an independent run an hour earlier; `KERNEL.md` §7 records the agreement). Demanding 55% there is demanding the kernel beat the decode stage. The floor is therefore:
  - **FMA-bound host → ≥55% of measured peak, unchanged.** This is the default and the common case.
  - **Issue-bound host → ≥90% of its issue roofline**, where the roofline is `r_max ÷ (R × I)` with `r_max` the host's measured issue ceiling, `R` its measured FMA/cycle, and `I` the **spill-audit's own counted instructions per FMA** for the shape being measured. Same 55% intent, expressed against what the lowering can express rather than against a number the front end forbids.
  - The roofline is **clock-free**, so the gate needs no `taskset`, no `perf` counters and no frequency measurement. With `f_i` the measured fraction of peak for mix *i*, the observed retirement rate is `r_i = f_i · R · I_i`, and `R` is common to every mix on a host, so it cancels from both the classifier (a ratio of rates) and the roofline: **`roofline(I) = maxᵢ(f_i · I_i) / I`**. Rates below are quoted in insns/cycle for legibility, but nothing in the gate reads a clock.
  - `r_max` is the **maximum** rate observed across the ceiling mixes, not the mean. A ceiling is an upper bound on what was observed, and taking the max raises the roofline and so tightens the criterion — on janus, max 4.37 gives a 48.6% roofline and 94.6% attainment where the mean 4.33 would have given 48.1% and 95.6%. The stricter reading is the one a gate should take, and the classifier's 10% convergence requirement already bounds how far max and mean can diverge.
- **A host is classified issue-bound by evidence independent of the fraction being gated.** This matters: the naive test — "measured issue rate < the rate 55% would require" — expands to `f·R·I < 0.55·R·I`, i.e. `f < 0.55`, which is just "the host failed the floor" wearing a derivation. It would make the amendment self-granting. The real test is whether an issue *ceiling* exists at all, which only structurally different instruction mixes can show: a host is issue-bound iff the retirement rates of its **ceiling mixes** agree within 10% while their audited insns/FMA differ by ≥25%. Convergence across mixes is a property of the machine; divergence means something other than issue width binds. Cross-checked by the clock-free inverse-throughput test (two shapes' throughputs stand in the inverse ratio of their instruction counts: janus 1.308 against 1.351 predicted, a 3% miss; vesta 0.957 and antares 0.828, 29% and 39% off).
- **The ceiling mixes exclude the shape being gated, or the roofline floor decides nothing.** Write `p_i = f_i · I_i` and let *b* be the shape under test. Then `attain = f_b ÷ (maxᵢ p_i / I_b) = p_b / maxᵢ p_i`, so if *b* is itself one of the mixes, `attain ≥ minᵢ p_i / maxᵢ p_i = 1/cspread ≥ 1/1.10 = 0.909` — already above the 0.90 floor, **as an algebraic identity**. Every host the classifier admitted would clear the floor by construction, and worst of all in the binding case: on janus the shape under test *is* the argmin of `p_i`, so `1/cspread` and attainment agree to four places (0.9476). The ceiling is therefore established by the *other* mixes — the alternate shipped shape plus the register-only peak kernel — and *b* is then judged against it, which makes the two tests independent measurements. The first implementation of this gate had exactly this hole; the derivation above is why `scripts/roofline.sh` is a separate, unit-tested pure function rather than inline gate logic.
- **A ceiling the machine exceeds is not a ceiling.** Excluding *b* invites the mirror abuse — understate the ceiling and any *b* clears it — so two things bound it. The peak kernel is always a ceiling mix with `f = 1` by definition, pinning `maxᵢ p_i ≥ I_peak` no matter what the alternates do, which means sandbagging an alternate *breaks convergence* rather than lowering the roofline. And if `attain > 1`, the issue-bound hypothesis is falsified by the very data offered in its support and the host reverts to the flat floor. This is not hypothetical: **antares (Zen 5) is returned to the FMA-bound branch by exactly this clause.** Its ceiling mixes converge to within 9.1% (2×32 and the peak kernel) over a 2.06× mix spread, which would classify it issue-bound with a 39.3% roofline — but its winning 4×32 shape retires **158.5% of that roofline**, 58% *above* the ceiling those mixes set, and 63% above it at the median before the confidence interval is deducted. No ceiling, no roofline: it faces the flat 55% and clears it at 62.3% net of CI.
- **The roofline branch carries an anti-vacuity guard, without which it is not a gate.** A roofline computed from the instruction count of the kernel under test rises as that kernel gets worse: pad the loop with a hundred dead instructions and it still scores ~100% of its now-terrible roofline. So on the issue-bound branch the shape must *additionally* be within 5% of the best zero-spill insns/FMA in the recorded shape sweep (`KERNEL.md` §3). The shipped 2×32 is at 4.625 against a sweep best of 4.438 — 4.2% over, inside the guard. This is what keeps "≥90% of roofline" from meaning "≥90% of whatever we happened to emit"; a +40-instruction padded 2×32 scores 94.7% of its self-inflated roofline and is refused. Note also that the classifier resists gaming in the same direction: a merely-slow kernel produces *divergent* rates across shapes, lands in the FMA-bound branch, and faces the full 55%.
- **What the amendment costs, as a number.** Because the peak kernel pins `maxᵢ p_i ≥ I_peak` and the shape guard caps the denominator at `sweep_best × 1.05`, the effective floor for an issue-bound host is never below `0.90 × 2.25 ÷ 4.659 = 43.5% of measured peak`. That is the entire slack the amendment grants: from 55% to no less than 43.5%, and only to a host that has independently demonstrated a front-end ceiling it does not itself exceed. "Never a number without its denominator" applies to the gate's own leniency.
- **The claims above are tested, not asserted.** The decision is a pure function, `throughput_verdict` in `scripts/roofline.sh`, and `scripts/roofline-test.sh` drives it with fixtures that attempt each abuse: a +40-instruction padded kernel, a merely-slow kernel on a wide host, a sandbagged alternate shape, a single-mix ceiling set, an issue-bound host at 75% of its roofline, and both threshold boundaries. Those controls run at the **top** of `gate-p2.sh`, before any benchmarking, because a decision function that admits a padded kernel would make every number after it meaningless.
- **Cause of the roofline, and the standing task to retire it.** The roofline is not a fact about the ISA; it is a fact about this lowering. Go's assembler already encodes the instruction a hand-written SGEMM K-loop wants — `VFMADD231PS.BCST 12(SI), Z1, Z0`, verified assembling to `vfmadd231ps 12(%rsi){1to16}, %zmm1, %zmm0` — which accumulates in place and takes a broadcast memory multiplicand, collapsing four instructions into one. The intrinsic layer cannot reach it for three separate reasons (`docs/toolchain-notes.md` T12, issues #17/#18/#20, filed upstream as golang/go#80828, #80829 and #80830): only the 213 FMA form has an SSA op, so accumulation cannot land in the accumulator; the load-merge rule that *does* exist folds memory into the 213 form's addend, which in a GEMM is the accumulator and the one operand that must stay in a register; and no SSA op or rule anywhere emits the `.BCST` suffix the assembler supports. **Standing task:** when a toolchain lowers `MulAdd` to a 231-shaped FMA with a folded broadcast operand, re-audit and re-measure janus. The shipped 2×32 body goes 74 → ~46 instructions and `I` goes 4.625 → ~2.875. Note that **231 alone is not enough**: folding the accumulate but not the broadcast leaves 66 instructions and `I = 4.125`, which projects janus to ~51.7% of peak — past the 49.1% its ratcheted roofline floor would then demand, but still under the flat 55%, so the host would remain issue-bound. The embedded broadcast is the larger of the two levers, and only both together put janus over the flat floor.
- **The amendment ratchets; it does not retire.** An earlier draft of this section claimed it was self-retiring — that once the lowering improved, janus would stop classifying issue-bound and the flat floor would resume. The arithmetic says otherwise, and says something better. The effective floor is `0.90 × maxᵢ p_i ÷ I_b`, and `maxᵢ p_i` is pinned by the peak kernel, so the floor is **monotone non-increasing in `I_b`**: every improvement to the lowering *tightens* this gate automatically. Post-fix janus stays at its front-end ceiling, but its roofline rises to `2.250 ÷ 2.875 = 78.3%` and its required floor to `0.90 × 78.3% = 70.4%` — stricter than the 55% the amendment replaced, and cleared by the projected ~74%. A post-fix kernel at 60% of peak would pass the flat 55% and **fail** the ratchet; that is a control in `scripts/roofline-test.sh`. So the amendment needs no expiry clause and grants no permanent dispensation: it is exactly as strict as the instruction set as-lowered permits, and it follows the toolchain up.
- **Peak is measured, not derived** (revised 2026-08-11, decision on issue #11). The original formula — cores·freq·2 FMA ports·16 lanes·2 flops — assumes two full-width 512-bit FMA units. Zen 4 has none: it double-pumps AVX-512 over 256-bit datapaths and retires one 512-bit FMA per cycle, so the formula overstates that host's ceiling by 2× and would turn a 55% floor into a demand for ~110% of the silicon. The denominator is instead `BenchmarkPeak` in `bench/`: `internal/vec`'s register-only FMA-saturation kernels (no memory in the loop, ≥8 independent accumulator chains, distinct chain starts so CSE cannot merge them), measured per host under the §5.4 methodology. The formula survives as a **printed cross-check only**; a measured/formula divergence of ≥1.5× is the double-pump signature and is reported as expected rather than as a fault. This keeps the 55% floor meaningful — it is 55% of what the machine demonstrably does — without hardcoding a microarchitecture table, and it carries to Zen 5 and to a future arm64 port unchanged.

### Phase 3 — Packing + blocking → full SGEMM (≈2 sessions)
- Goto three-level blocking: NC (B panel → L3), KC (depth → L2 residency of A panel), MC (A panel → L2), then MR×NR microkernel over L1. Initial params for a Zen4/Ice Lake-class target: KC=384, MC=144 (multiple of MR), NC=4096 (multiple of NR); make them vars, auto-tune later.
- Packing routines SIMD-accelerated through the shim; transpose flags handled here.
- Edge kernels: masked loads/stores for M%MR, N%NR remainders (the simd API's mask support determines whether this is masked ops or a scalar fringe — read the API, then choose; scalar fringe is acceptable at these sizes).
- Beta handling (β=0 ⇒ no C read; β=1 ⇒ no multiply) as kernel variants, not branches in the loop.
- **Gate P3:** full `Sgemm` matches oracle across a size sweep (1..17, 63,64,65, 500, 1000, 2048, plus transpose/beta/alpha combinations); single-thread ≥60% of OpenBLAS at 2048³ (bench harness pulls OpenBLAS via build-tagged cgo, dev machine only, never a package dependency).
- **The reference is same-host OpenBLAS, on every gate host** (amended 2026-08-11, ruling on the provisioning question; issue #23). OpenBLAS is installed on all three amd64 gate hosts and the ratio is evaluated per host against *that host's own* OpenBLAS, in the same benchmark invocation. No cross-host reference and no designated golden machine: the only apples-to-apples ratio is same silicon, same thread count, same run — §7 rule 7 with no exception carved for convenience. The dev host stays what `docs/hosts.md` argues it is, plumbing verification only; its Homebrew OpenBLAS dispatches to the M4's matrix unit (`vortexm4`, ~1410 GFLOP/s from one thread, ~10× what that core's NEON FMA pipes can issue) and answers a different question than the gate asks.
- **The reference's own configuration is provenance, and the gate refuses a flattering one.** OpenBLAS version and the DYNAMIC_ARCH-selected kernel name are recorded beside every ratio, and `OPENBLAS_NUM_THREADS=1`/`OMP_NUM_THREADS=1` enforcement is both applied and *verified* from the library's own `openblas_get_num_threads()`. A distro package that quietly selects a pre-AVX2 kernel on an AVX-512 host reads low, which inflates keel's ratio — the one direction a gate must never fail in — so the selected kernel must be an AVX2-or-better µarch target or the criterion fails. An unrecognized new target name also fails, loudly: missing knowledge should cost a human a minute, not silently widen a bar.
- **The reference is the fastest *measured* same-host OpenBLAS over a coretype sweep, not whatever `DYNAMIC_ARCH` selected** (amended 2026-08-11, ruling on issue #31). Each host's reference is measured under `{default, Zen, Haswell, SkylakeX, Cooperlake, SapphireRapids}` forced through `OPENBLAS_CORETYPE`, best-of-N under §5.4's methodology, and the fastest is pinned for the run that produces the ratio. **Every candidate's `corename` and rate is recorded in the provenance block, not just the winner**, and the pin is verified from the library's reported `corename` rather than trusted from the environment. The allowlist of the previous bullet keeps its narrowed job — the *floor*, "modern enough" — and the sweep supplies the *ceiling*, "the best this silicon can do". Why the change: `DYNAMIC_ARCH` dispatches on an ISA feature check, so on vesta's Zen 4 it ships a full-width Cooperlake kernel onto a double-pumped 256-bit datapath and the AVX2 `Haswell` kernel measures **6.7% faster** (159.5 vs 149.5 GFLOP/s), while antares (Zen 5, full-width) and janus (Skylake-X) both select correctly. That is keel's own #24 bug with the vendors reversed, and it means "whatever the library picked" delegates the denominator's one inviolable property — that it never flatters keel — to an upstream heuristic measured wrong on one of three hosts. Same move as #11's measured-peak ruling: measure the denominator instead of trusting a selector, which also needs no µarch table to maintain and survives every future host and OpenBLAS bump. This binds whether or not it changes a verdict: where the `min` of the next bullet makes it provenance-only, a provenance block recording a reference known to be 6.7% low is still a defect in the evidentiary record.
- **The performance governor is asserted on every host, not assumed** (same ruling). `gate-p3.sh`'s preamble and `provision-openblas.sh` both read `scaling_governor` per host and fail on anything but `performance`; unreadable counts as unmet, and the gate re-reads it at measurement time so a governor that changed after the preamble fails that host instead of passing on a stale check. The gate used to read it and only *label* the OpenBLAS pass line with it — a tally any single host could satisfy — which let antares measure on `powersave` — where its first OpenBLAS reading was 245.0 GFLOP/s against a 296–297 steady state, a ramping-core artifact indistinguishable in a log from a slow machine. Same discipline as reading `threads=` back out of the library: a precondition that is not checked is a precondition that drifts.
- **On an issue-bound host the P3 denominator is `min(same-host OpenBLAS, roofline × measured peak)`** (same ruling; cause is #17/#18, `docs/toolchain-notes.md` T12). OpenBLAS on Skylake-X is hand assembly whose K-loop folds accumulation and an embedded broadcast into single FMAs — instructions the intrinsic layer provably cannot emit — so it lives *above* the front-end ceiling that caps keel's kernels. Asking keel for ≥60% of that is asking the decode stage, not the kernel, and P2 already adjudicated that root cause rather than leaving it as keel's defect. So keel is asked for ≥60% of what its instruction stream *as-lowered* can express. Four properties keep this from being a dispensation:
  - **It only ever lowers the denominator, and only for a host that independently demonstrated a front-end ceiling** by the P2 classifier (ceiling mixes converging within 10% over a ≥25% mix spread, the shape under test not exceeding the ceiling it sets). FMA-bound hosts are untouched: vesta and antares face the plain, unmodified criterion, so at least one host measures the comparison with no assistance at all.
  - **The roofline is the one belonging to the shape `Sgemm` actually ran**, read from the `keel-bench-kern` marker of the very run that produced the ratio, and it carries P2's anti-vacuity shape guard unchanged: a shape more than 5% above the sweep's best zero-spill insns/FMA is refused a roofline outright and the host reverts to the plain OpenBLAS denominator. A fatter kernel cannot buy itself a lower bar — which is not hypothetical here: the guard refused the then-dispatched 4×32 (6.250 insns/FMA against a 4.438 sweep best) while only the 2×32 the sentinel gated (4.625) was inside it, and that red is what surfaced issue #24. Dispatch was shipping a shape janus demonstrably should not run, and the guard declined to paper over it with a forgiving roofline; the fix was the dispatch bug, not the guard, and the next bullet is the ruling.
  - **It ratchets exactly as P2's floor does.** The roofline term is `maxᵢ p_i / I`, monotone in the gated shape's instruction count, so every improvement to the lowering raises it; when it rises above same-host OpenBLAS the `min` picks OpenBLAS and the amendment retires itself with no expiry clause to remember. Same standing task as §4/P2: when a toolchain lowers `MulAdd` to a 231-shaped FMA with a folded broadcast, re-audit and re-measure janus, which then reverts to the plain reference.
  - **Both ratios are always printed**, amended and plain, on every host. The gate's leniency is itself a number with a denominator; hiding the unassisted figure would be the reporting failure §7 rule 7 exists to prevent.
- **Microkernel shape is selected per host, by the same issue-bound/FMA-bound classification** (amended 2026-08-11, ruling on issue #24). P2 shipped two zero-spill shapes and `KERNEL.md` §7 measured the winner flipping between them: 4×32 on Zen 4 and Zen 5, 2×32 on Skylake-X by 11 percentage points. Dispatch took the registry's first entry, so it ran 4×32 everywhere — a performance bug on one of three hosts, and the one the roofline guard then refused. So `Sgemm` now classifies the host and picks the shape extremal on that class's binding cost: an FMA-bound host takes the fewest memory ops per FMA (4×32, 0.75), an issue-bound host the fewest instructions per FMA (2×32, 4.625). This is not a weakening; per-target microkernel shapes are what BLIS and OpenBLAS both carry, "one shape everywhere" was never a principle here, and P2's own data proved the physics — on janus the two shapes' throughputs stand in the inverse ratio of their instruction counts. Three properties keep it honest, and `KERNEL.md` §8 is the record:
  - **The gate requires that the shape measured is the shape dispatch selects.** The throughput sentinel judges the dispatched shape rather than whichever shipped shape measures fastest — with a per-host choice those stopped being the same claim — and the other shapes become its ceiling set. Both are benchmarked in one invocation, so "did dispatch pick the faster one" is answered from the same measurement: if a passed-over shape's lower bound clears the dispatched shape's point estimate, the gate fails. The blocked `Sgemm` at 2048³ is then re-measured with `KEEL_KERN_CLASS` pinned to the other class, as a cross-check on the number the criterion actually rests on.
  - **The classification is a proxy, so it is checked against measurement on every host, every run.** `archsimd` reports CPU features and never a vendor, family or model, and `internal/cpu` discards the CPUID signature word, so no microarchitecture is readable from pure Go here (`docs/toolchain-notes.md` T14, issue #25). `kern.HostClass` fingerprints the generation from a feature bundle instead — AVX-512 with VBMI2+VPOPCNTDQ is Ice Lake / Zen 4 or later — and the library prints its verdict and its grounds so the gate can compare them against the class its own convergence test derives from the measurements. Disagreement is a gate failure. Neither error direction can make a gate lenient: a wrongly-FMA-bound host dispatches the fat shape, which the roofline guard then refuses, making the bar *stricter*; a wrongly-issue-bound host gives up throughput, which the same-invocation shape comparison catches.
  - **The instruction counts the ranking reads are re-derived from the object code.** `Kernel.InsnsPerFMA` is a measurement recorded in Go source, and it decides what ships, so the gate recounts every shipped shape's loop body in the spill audit and fails on disagreement. An unaudited shape is unrankable rather than lean, which is a second lock on the spilling reference tile never being selected.
- **One re-run for a failing sentinel reading, and the retry is part of the record** (added 2026-08-11 by ruling, recorded on issue #4; this is an allowance granted to the gate model, not one the implementer may grant itself). A *throughput sentinel* criterion — P2's ≥55% floor, and its P3 successor requiring ≥90% of the dispatched shape's roofline on an issue-bound host — that reads as failing triggers exactly one immediate re-run; the criterion fails only if **both** runs fail. **Both outputs are archived in the gate record either way** (the session-end comment on the phase umbrella issue, pasted verbatim per `CLAUDE.md`), so a gate that passed on the second reading visibly says that it did, and a run of retries would be legible as one. This is a statistical allowance, not a mulligan: one retry, never a loop, and **never applicable to a correctness criterion** — oracle sweeps, differential tests, spill/call/BCE audits and the shape-agreement checks fail on first miss, because a differential test that passes on retry has found a nondeterminism worth more attention than the gate colour, not less.
  - It exists because janus's roofline attainment is the tightest margin in the gate and the only criterion whose ordinary variance can straddle its bar: two independent runs an hour apart read 95.0% and 93.7% against ≥90%. Writing that down converts a future fire drill into a documented allowance; leaving it as an operator's instinct is how "re-run once" decays into "re-run until green".
  - `scripts/gate-p3.sh` itself is unchanged and still fails on the first miss — the allowance is the operator's, and the archive is what keeps it honest. A gate that retried internally would have to be trusted to report that it had; a human re-run that must paste both outputs into the umbrella issue is auditable by construction. The friction is the feature: the allowance costs one deliberate act every time it is exercised, and this criterion is the last one in the project that should be optimized for convenience.
  - **How often it is needed is itself the signal.** Each retry is compliant on its own, so "one per reading" alone would permit a criterion retried indefinitely. The interpretive rule: a sentinel that needs its retry often enough for the friction to hurt is not noisy — it is reporting that the margin is gone, and the response is to raise the throughput or re-derive the bar, never to keep spending the allowance. Because every exercise is archived verbatim in the umbrella issue, the frequency is legible in the record rather than something anyone has to remember.
- **A verdict cannot be more certain than the least certain link in its derivation chain, so the host classification is graded in three states** (ruled 2026-08-16, issue #86). The classification is not a result; it is an *input* that four criteria divide by. When the measurement cannot decide it, the class is **`indeterminate` for that run** and every criterion consuming it reports `UNMEASURED` naming one cause — "classification indeterminate this run" — rather than each inventing its own failure. That is §5 rule 6 applied one level up the chain: one cause, one label, and an absent measurement gets `unmeasured` and never a red attributed to something else — so no healthy numerator is judged against a denominator chosen by noise, and no log line dispatches the operator to repair a fingerprint that was right.
  - **What happened.** On 2026-08-15 (`build/gate-p3-under-p4-708ddbb-run1.log`, and the healthy re-run at the same commit beside it) janus's classify invocation read both microkernels low against the peak kernel measured in the same invocation. The ceiling spread crossed 1.10, so the convergence test returned `why=diverge`, the host reclassified fma-bound, and **four verdicts moved on that one link**: the class-agreement check failed and told the operator to fix `internal/kern.HostClass`'s fingerprint; the sentinel faced the flat 55% instead of 90% of its roofline and failed at 42.7% of peak; criterion 6b's denominator switched from `roofline 105.52` to `openblas 194.35`, turning 75.1% into 39.5%; and criterion 6's aggregate followed. Against a *fixed* denominator the same two readings differ by 1.3 points (39.5% vs 40.8% of plain OpenBLAS). The 35-point swing was the denominator, not the kernel.
  - **The straddle test goes on the class-selecting comparisons, not on the result boundaries.** Two comparisons select the class from measured fractions: the ceiling spread against `converge_max` (1.10) and attainment against 1.0 (the falsification test). Both now take interval ends — `bench_ratio_lo`/`bench_ratio_hi` from §5 rule 5, measured, never a symmetry assumption about the point estimate. Clear of the bar on either side with a clean reading keeps its two-state answer, including the genuine class-disagreement failure this gate is *supposed* to raise; an interval that spans the bar yields `indeterminate`. The result boundaries — attainment against the 90% roofline floor, best-of-peak against the flat 55% — are self-contained and **stay two-state**, with §4's one archived re-run. With zero-width intervals the three-way tests reduce exactly to the two-way ones they replace, which is why every control written before this amendment keeps its verdict — the 29 that predate it are unedited (`scripts/roofline-test.sh`, 43 fixtures now).
  - **And no verdict *less* certain than its derivation requires: an undecided comparison whose branches agree decides the class anyway** (added 2026-08-16, same issue, before the amendment's first green run). The law above has a second edge, and the first cut of the amendment implemented only one of them. When the ceiling spread's interval straddles `converge_max`, *both* readings of that straddle can still lead to the same class: converged means the ceiling exists and attainment above it **falsifies** it (fma-bound), and not converged means no ceiling was established at all (fma-bound). Neither branch reads `roof`, and the flat floor that then applies is the same expression in both — so withholding the class there would be an `UNMEASURED` the data settles, which is this same defect pointed the other way. Reported as `why=falsifiedanyway` and `why=samemixanyway`, with the straddling interval still printed, so the record says *could not decide this, did not need to*. Two properties make it a measurement rule rather than an escape hatch: the collapse is tested over the **whole** interval — `roof_hi = pmax_hi / I` is the highest ceiling the reading admits, and falsification must hold at every point of it, never at the midpoint — and it can only ever move a host from `indeterminate` to a class it was already going to get on both branches, never between classes. **Found by a real reading grazing the bar rather than by review:** on 2026-08-16 antares measured a spread interval of [1.077, 1.100] against the 1.10 bar while retiring at 162.2%–165.2% of the roofline that interval implies. One rounding step higher and a host falsifying its claimed ceiling by 62% would have been reported "classification indeterminate".
  - **The three-state renderings are exercised on purpose, because a branch in the certifying instrument that has never run is untested** (authorized 2026-08-16). On this fleet they are otherwise unreachable — janus's class-selecting interval is zero-width, so no value of the 1.10 bar can sit inside it, and antares's attainment is 162%, nowhere near 1 — so the synthetic input goes on the **measurement** side, not the threshold: `KEEL_INSTRUMENT_WIDEN_CI=<pct>` widens each ceiling-set mix's interval around its own point estimate, which reproduces the 2026-08-15 condition (a host reading noisily) rather than a bar nobody would ship. Every shipped threshold prints in the log unchanged, every verdict line carries a `[synthetic]` stamp, the run prints **neither GREEN nor RED** and exits 2, and the artifact lands at `build/instrument-exercise-*` and never on a `gate-pN-<rev>` path where a reference-hungry diff could pick it up (#78). Same discipline as the `fakessh` dead-host arm and the must-fail fixtures: an induced failure is legitimate exactly when the artifact cannot be mistaken for evidence.
  - **Why §4's re-run allowance is not the remedy here and stays where it is.** That allowance was priced for one verdict: one deliberate re-run, friction as the feature, archived both ways. A propagating *input* spends four verdicts per exercise, which is a different purchase than the one §4 authorized. So the allowance stays for self-contained sentinel reds, and derivation inputs get the straddle test instead. Re-measuring an `indeterminate` is not the allowance being spent — there is no verdict to overturn — and it is therefore uncapped; the §4 frequency clause's logic still applies in spirit, since a host chronically undecidable here is reporting that its intervals are too wide for this bar.
  - **It withholds PASSes too, which is what makes it a measurement rule rather than leniency.** An attainment interval reaching above 1.0 is undecided about whether the host has already beaten the ceiling it claims, and a host cannot be graded against a roofline it may have falsified. Control 23 in `roofline-test.sh` is that case: 98.7% attainment, which would sail past the 90% floor, reported `UNMEASURED`.
  - **The gate now prints the quantity it decided on.** `gate-p3.sh` discarded both the ceiling spread and the mix spread (`read -r ... _CSPREAD _MSPREAD`), so when the classification flipped, the number that flipped it was nowhere in the log and had to be bounded backwards out of the threshold — which is how the first reconstruction of this incident got the wrong link, blaming the 90% floor. Both spreads and the attainment interval now print per host per run, against the bar each is judged by — §5 rule 8's "publish the underlying pair beside the derived figure" clause, applied to a class instead of a percentage: the derived figure was the classification, and its underlying pair was in no log.

  - **The ratio criterion is graded in three states, not two** (ruled 2026-08-15, issue #67). The bar and the pass condition are unchanged: a host passes iff the ratio's conservative lower bound — numerator down by its CI, denominator up by its own, §5.5's methodology — is ≥85%. What changes is the negative answer, which used to mean two different things at once. A host **fails** only when the *whole* interval sits below 85%, which is a claim about `Ssyrk`. When the interval **straddles** the bar the reading is `unmeasured`: the gate stays not-green, and the log says the measurement could not decide rather than that the kernel is slow. §5.6 forbids one verdict standing for two causes, and this criterion was violating it — janus read 87.6% raw with ±4.0%/±3.0% intervals and failed, then read 87.0% raw at ±0.0% on the same tree at the same commit and passed. The raw quantity agreed to within 0.6 points; the FAIL was reporting the weather.
  - **The remedy for `unmeasured` is precision, never a wider judgment.** §4's one archived re-run applies as it does to any throughput sentinel, and the frequency clause applies as written: a host *chronically* undecidable here is telling you its intervals are too wide for this bar, and the response is a higher `-count` for this criterion on that host. Grading the raw ratio instead of the bound would let a genuinely-below ratio clear on a lucky draw, which is the failure this state exists to prevent. The **flip-headroom** — the symmetric CI at which the bound would land exactly on the bar, `(raw − bar)/(raw + bar)` — prints per host per run so the record shows how close each verdict ran to undecidable: at the 85% bar it is 4.17% on the 7950X3D, 1.16% on the i9-9960X and 1.85% on the AI MAX+ 395, against intervals those hosts produce up to 1.0%, 3.0% and 2.0% in one gate run. Two of three decide this criterion on how quiet the machine was, and nothing in the log said so until it was printed.

### Phase 5 — Parallelism, dispatch, polish (≈1–2 sessions)
- Parallelize the MC (ic) loop over a bounded worker pool sized by `runtime.GOMAXPROCS(0)`; shared packed-B panel per NC iteration, per-worker packed-A buffers from a `sync.Pool`. No background threads, no state between calls.
- Runtime dispatch finalized, and **the chain is per level, not one chain for the library** (narrowed 2026-08-12 by ruling, issue #40): **Level 1 dispatches `avx512 → avx2 → scalar`**; **Level 3 (the GEMM microkernel and everything blocked around it) dispatches `avx512 → scalar`**. Overridable by env `KEEL_FORCE=scalar|avx2|avx512` for testing, where `avx2` acts as a *ceiling* at Level 3 rather than a panic, so a legitimate Level-1 configuration can still call `Sgemm`; `ActiveKernBackend` then reports `scalar`, so no marker can believe it measured an AVX2 SGEMM.
  - **Why Level 3 advertises two rungs and not three.** `internal/kern` has no AVX2 microkernel, so the middle rung of a three-rung Level-3 chain would be unmeasured — and unmeasurable on the machines this project has. No gate host is AVX2-only silicon, and `KEEL_FORCE=avx2` on an AVX-512 machine establishes *correctness* under forced narrowing, not *performance*: front-end and port behaviour on a part that has AVX-512 is not evidence about a part that does not. An advertised chain whose middle link no gate can back is a claim, not a measurement, and §7 rule 6 forbids exactly that shape of claim. Level 1 keeps its AVX2 path because it is measured and has been gated since P1.
  - **The AVX2 microkernel is deferred with its unblocking condition named, not dropped:** an AVX2-native evidentiary host (real silicon with no AVX-512, so the kernel can be *measured* rather than merely exercised). Debt with a trigger. Correctness of any future AVX2 kernel remains testable on existing hosts via `KEEL_FORCE`; only the performance claim needs the new machine.
- The package must compile and pass (scalar path) *without* `GOEXPERIMENT=simd` — build tags make the fast paths additive. This is what lets it exist on proper `go get` terms the day the experiment graduates.
- Scaling benchmark, README with honest numbers, `doc.go`.
- **Named input carried in from P3: close janus's retention gap (issue #26), don't regress the Zens** (added 2026-08-11). This is the "make them vars, auto-tune later" half of P3's blocking work coming due. The blocked `Sgemm` keeps about 90% and 92% of its own microkernel's throughput on vesta and antares but only about 77% on janus, so roughly 13 points of Skylake-X throughput are sitting in packing, memory traffic and loop-nest overhead — *not* in the front-end ceiling the P3 roofline models, which is why the amendment neither excuses it nor nets it out. `KC=384 MC=144 NC=4096` were chosen once and never swept per host. `scripts/gate-p3.sh` prints retention per host on every run as reported-never-judged provenance, so this phase starts from a re-runnable measurement rather than a remembered one, and the success criterion is written by that number: bring the issue-bound host toward the retention band the FMA-bound hosts already sit in, without moving them down.
- **P5 is ordered internally: single-thread remediation, then the parallel loop nest, then the scaling gate** (added 2026-08-12 by ruling; sequences #26, #36, #37 and the deferred measurements on #21/#22 ahead of the parallelization). The four deferrals are single-thread costs that parallelization multiplies rather than hides, which makes each of them a scaling bottleneck waiting to be measured. If the parallel work landed first, the gate would certify scaling curves for routines the phase then intends to change, every number would need re-measuring, and the record would carry two regimes with no way to say which one shipped. Same reasoning as P3 keeping the hardened re-run rather than the green it inherited: **the certifying measurement comes last, over the final artifact.** #21 and #22 are taken in the same campaign as #36 and #37 because they are the same territory — packing and edge handling in the single-thread nest — and re-entering that code twice is how a measurement gets compared against a different build than the one it was taken on.
- **janus stays a gate host in P5, under the same issue-roofline exception it was granted in P2/P3** (confirmed 2026-08-12 by ruling, on the question of whether a host at 31.9% of peak should keep certifying phases). It is the only Intel host, the only issue-bound host, and the designated sentinel whose number moves when the lowering improves — the standing task in the roofline section above names it by name. Under the ratcheting amendment the exception is principled rather than lenient: the floor is monotone non-increasing in `I_b`, so every toolchain improvement *tightens* what janus must clear. Dropping it would remove the machine that has carried the most information per run of any host in this project; the moment it becomes inconvenient is the moment it is working.
- **The `-race` criterion is not amendable to exclude `checkptr`** (ruled 2026-08-12, issues #42/#22, `docs/toolchain-notes.md` T17, upstream golang/go#80856). `archsimd`'s partial slice load/store manufacture a full-width `*[16]float32` from a short slice, so `go test -race` is a *fatal error* — demonstrated through keel's public API on a 1×1 `Sgemv`. Race-clean is table stakes for a Go library, and `checkptr`-clean is what race-clean means for code holding `unsafe`; excluding the pointer checker would certify keel safe minus the instrument that checks. So keel takes the local workaround, and it lands **inside #22's edge-handling campaign** rather than as a point patch: **`checkptr`-cleanliness is an admissibility condition on #22's candidates, not a competitor in the measurement** — masked-partial is measured against zero-padded-panel among `checkptr`-clean implementations only, and a faster variant that fatals under the pointer checker is disqualified rather than ranked. Admissibility first, then speed.
- **Stage 3 gets an evidentiary `.metal` host, and the ≥6× floor is unchanged by it** (added 2026-08-12 by ruling, issue #12). The floor was written when the largest gate host had 16 cores, and 6× at 8 threads on a client part with client memory channels does not locate where the parallel nest stops scaling: packing-buffer contention that is invisible at 16 threads is the whole show at 64. So stage 3 measures its scaling curve on a bare-metal server part — `c7i.metal` (Sapphire Rapids, true 512-bit datapath, mild AVX-512 licence) and `c7a.metal` (Zen 4 server), ideally one of each since the scaling *shape* is expected to differ by class — with real core count and real memory bandwidth to scale into, and correctness-class spot instances widening the µarch sweep separately and cheaply.
  - **This adds hosts to the criterion; it does not move the criterion.** ≥6× at 8 threads on 4096³ stays exactly as written, and every gate host must clear it, so a new machine can only make the gate stricter. The wider curve (16/32/64 threads) is **reported beside** the judged number, in the same reported-never-judged position retention holds — a threshold at 64 threads would be invented after seeing the data, which is the move §7 forbids.
  - **Bare metal rather than a vCPU, for the reason #12 gave about P2:** on shared tenancy a noisy neighbour and an invisible frequency ceiling are indistinguishable from a bad loop nest. A number that certifies a phase should not have that ambiguity in it.
  - **Launched when there is something to measure, not before.** The parallel nest is stage 2's output; a metal host running during stage 1 would bill for hours and measure nothing. Provisioning goes through `truffle`/`spawn` under `AWS_PROFILE=aws`, each host gets a `docs/hosts.md` entry with its class recorded, and everything is torn down at session end. Gates keep running on the local hosts: a gate that depends on a paid resource being up is a gate that goes red for billing reasons, which is #12's own recommendation and is not weakened by using EC2 for the published curve.
- **Gate P5:** ≥6× single-thread throughput at 8 cores on 4096³; race detector clean; `go vet`/`golangci-lint` clean; scalar-only build green on stock toolchain. Retention stays reported rather than judged: #26's target is a direction to work in, not a threshold invented after the fact.
- **The scaling floor binds by parallelism class, not by routine list** (added 2026-08-12 by ruling, on the question of whether P4's derived routines are judged or only `Sgemm`).
  - **`Sgemm`, `Ssyrk` and `Ssymm` are one class and the ≥6× floor binds all three.** They are GEMM-shaped nests over independent tiles with no cross-iteration dependence, so the same parallelization is available to each by construction. Judging only `Sgemm` would let a serialization bug in the triangular C-update masking hide behind "the derived routines are reported, not judged" — precisely the routine where a subtle dependence would be introduced, and precisely the measurement that would have caught it.
  - **`Strsm` is a different class, and its floor is deferred to a measurement.** Its diagonal solves impose a dependency chain the other three do not have, and the parallelism available to it depends on `side` and shape in ways theirs does not. Writing 6× on it now would be inventing a threshold without a model, which this project has refused five times. So P5 measures `Strsm`'s scaling, reports it beside the judged three, and states the parallelism model behind it — what fraction of the work at the gate's shape is rank-update versus diagonal solve. That measurement and that model set its floor, which **binds from the commit that records it forward**. The deferral is recorded on issue #37 so it is a debt with a name rather than a permanent exemption.
- **Both arms of the scaling ratio run with boost disabled, and the boost-on speedup is reported beside the judged one** (amended 2026-08-15 by ruling, issue #66). As first written, "≥6× single-thread throughput at 8 cores" divided an 8-thread rate by a 1-thread rate measured on an otherwise idle machine. A single thread runs in a frequency regime eight threads physically cannot enter, so that denominator asks the nest to overcome silicon boost policy *before* it is permitted to demonstrate scaling. **A denominator measured in a regime the numerator cannot legally enter is not a ratio, it is a handicap.**
  - **The diagnosis came from the data, not from the inconvenience.** The two hosts that missed the floor are the two that retain the *most* of their own single-thread peak (Zen 4 at 92%, Zen 5 at 59%), while Skylake-X at 35% — the most serial-side headroom of the three — cleared all four routines, twice. Scaling deficits do not order themselves by single-thread excellence; boost tables do. Under the original reading the criterion would have been judging AMD's boost policy and reporting the verdict as a fact about keel's loop nest. That is §5 rule 6's misattributed verdict and §5 rule 7's relocated blame in one object: the instrument measured something real, correctly, and attributed it to the wrong stage.
  - **The amendment.** Both arms run with boost off — `/sys/devices/system/cpu/cpufreq/boost` on the AMD hosts, `/sys/devices/system/cpu/intel_pstate/no_turbo` on the Intel one — set in the gate preamble and **read back**, exactly as `scaling_governor` and OpenBLAS's `corename` are read back rather than trusted. **Unreadable counts as unmet**, never as satisfied. Numerator and denominator then sit in one frequency regime and ≥6× binds there.
  - **The boost-on wall-clock speedup against the idle single-thread rate prints beside it at equal prominence, reported-never-judged.** That is the number a caller actually experiences, and no reader gets to see the pass without it. Same shape as janus's sentinel line, where `46.1% of peak = 94.8% of its 48.6% issue roofline` puts the judged figure and the contextual one in one sentence so neither can travel alone.
  - **This makes the criterion easier in one direction and that is stated, not buried.** Boost-off lowers the 1-thread arm more than the 8-thread arm, so ratios rise. The justification is not that the new number is nicer but that the old one was not a ratio; the honest consequence is that boost-off ratios are **not comparable** to the three boost-on runs already in the record, and the record says so wherever both appear.

## 5. Testing philosophy (for the whole project)

1. **Oracle-driven:** float64 reference for every routine; the tolerance helper is the only place epsilons live.
2. **Differential across backends:** avx512 vs avx2 vs scalar on identical inputs must agree within reassociation tolerance — catches shim bugs independent of the oracle.
3. **Adversarial shapes first-class:** every dimension in {0,1,MR−1,MR,MR+1,…}; strides > width; overlapping aliases where BLAS defines behavior.
4. **Benchmarks are tests:** perf gates run in CI-mode locally (`go test -run=NONE -bench=Gate`) and the gate script parses the numbers. A silent 2× regression should fail a gate, not await a human.
5. **Gate benchmark methodology** (revised 2026-08-11, decision on issue #14): `-count=10 -benchtime=1s`, **every** measuring host under the `performance` governor — asserted per host, at the start of the gate and again at the moment of measurement, never assumed and never satisfied by one host on behalf of another, because a criterion that can be met vicariously is not a criterion — aggregated by `benchstat` (pinned as a module tool, so the version is in the repo). The gate compares **medians**, and a threshold counts as cleared only if it is cleared **net of benchstat's reported confidence interval** — numerator down by its CI, denominator up by its own. A distribution too wide for benchstat to bound is a failure to measure, not a pass. `-benchtime=3x` remains acceptable for smoke runs that inform no gate. Rationale: P1's first ratios came from `-benchtime=3x -count=5` reduced by min-of-samples, whose raw samples spread by 3.08× inside a single backend; ten one-second runs collapse that to low single-digit percent, and "clear the bar net of CI" means no gate can go green on a lucky run. Mechanics live in `scripts/bench.sh`, shared by every gate so none can quietly deviate.
6. **A gate red for the wrong reason is as untrustworthy as a gate green for the wrong reason.** A gate's product is verdicts, and a verdict whose cause is misattributed corrupts the record in either colour: it is remembered as what it claimed to measure, and what it actually measured is never revisited. Two P3 defects landed on one run and each produced a plausible verdict naming the wrong cause — a `-bench` filter that never ran the reference benchmark (#32) and a rate parser that read a theoretical-peak provenance line as a measurement (#33). The structural consequence, not merely the lesson: **every gate criterion that consumes benchmark output declares the benchmarks it will read and asserts a minimum row count for each of them before reading any of them.** An absent measurement must have exactly one verdict available to it — *unmeasured* — never a silent pass and never a red attributed to something else; `bench_expect` in `scripts/bench.sh` is where that is enforced, because `bench_stat` printing nothing is otherwise indistinguishable at every call site from a benchmark that ran and reported nothing under the unit asked for. Declared, then checked, which is the contract structure of the rest of the gate. Two corollaries with teeth: causes that differ must produce distinguishable verdicts even *inside* "unmeasured" (no rows at all, fewer rows than `-count`, and rows without the unit have different causes and are reported separately); and an instrument that cannot discriminate fails rather than returns a value, so a candidate sweep whose distinct families all measure the same rate is broken by construction and says so instead of crowning a winner by list order.

7. **A check that could not have come out otherwise is not evidence.** Two confirmations in one campaign turned out to be structural rather than evidential, and both were caught in-house rather than by a reviewer, which is what makes this a named trap instead of a recurring surprise. (a) *The tautology trap* (#48): a "second, independent" check on per-call flatness was the ratio `4.00 ÷ (per-call rise)` — a total is per-call cost times an exact call count, so the ratio is arithmetic performed on the very quantity it claimed to corroborate. It checked to the digit on both hosts and carried no information the per-call column did not already have. A number that agrees is not a check if disagreement was impossible. (b) *The unvaried control* (#8/T18): two repro arms differed in **two** ways at once — where a definition sat relative to the loop, and whether it arrived through a callee — and the effect was attributed to the salient difference. Three variables were dutifully held (accumulator count, loop count, masked tail) and every one of them was irrelevant; the one that mattered was never varied alone. The standing order, in two questions: for every confirmation, name the result that would have falsified it; for every isolation, name the single variable that differs between the arms. "Nothing could have" and "two things differ" both mean the check is not yet a check. **Corollary for compiler forensics,** from (b): blame flows upstream through the pass pipeline, so a pass whose fingerprints are on the assembly may be operating correctly on the output of a pass that did nothing. The allocator reusing a register holding a dead value was right; the missing hoist that left the value dead there was the defect. Idle registers next to a clobber are not evidence of an allocation decision.

8. **A summary is a cache with no invalidation protocol.** Every derived figure — a percentage, a ratio, a delta — is recomputed from the log it came from at the moment it is written, never carried forward from a prose summary, an earlier message, or a previous draft of the same document. Three occurrences across two authors, the third produced while this entry was being written, which is what makes this a named trap rather than a slip: vesta's *unblocked* microkernel percentage was carried into a sentence about its *blocked* `Sgemm`, which is a different denominator; `KERNEL.md`'s loop ratio needed explicit re-labelling during the layout ensemble for the same reason; and a session summary's `gate-p5: 64 PASS / 7 FAIL` was published in prose and repeated once before the log was consulted, which says `64 PASS / 5 FAIL` — five being the four unmeasured `-race` criteria plus the carried gate-p4, with no sixth or seventh to name. The mechanism never varies — prose drops the qualifier that made the number specific, and nothing downstream can tell that it is missing, because a figure with the wrong denominator is still a well-formed figure. Two consequences: **the number and its arithmetic are produced in one step** (grep the log, let `awk` divide, print), and **the underlying pair is published beside the derived figure** so a reader can check the division without the log. 
   **And recompute the same quantity, not merely from the same log** — this rule's own failure mode, which has now cost more than the trap it prevents. Rule 8 instructs distrust of the published figure and trust in the fresh recomputation, so recomputing a *different* quantity from the right log yields a well-formed number that disagrees with a correct publication, with the rule having pre-committed the writer to believing theirs. Two occurrences, both while this rule was being written. The #21 comment recomputed 8-thread **rates** against a table captioned "change in the 8-thread **scaling ratio, net of CI**", declared several cells wrong and published that; all twelve were correct, and the withdrawn `16.2 / 6.7 / 10.9` was correct too. One pair of logs answers "how much did Sgemm gain on janus" three ways — +6.22% (8-thread rate, 466.2 → 495.2 GFLOP/s), +4.22% (raw ratio, 6.211 → 6.473), +3.20% (ratio net of CI, 6.090 → 6.285) — because the change moved the 1-thread denominator too (75.06 → 76.50). A coincidence supplied the false confirmation: Ssymm/janus's ratio delta is +6.21% and Sgemm/janus's rate delta is +6.22%, so a matching figure read as a copied cell. The second occurrence is smaller and was caught before publication: the #66 boost-off smoke figures differ by aggregation, 19.6% and 5.91× under the mean against 19.8% and 5.90×→6.32× under the median, and `scripts/bench.sh` fixes the convention at *"the median net of benchstat's reported confidence interval"* — so **aggregation is part of a quantity's definition**, not a detail below it. Therefore: read the caption's *definition* of a figure before recomputing it, and treat a disagreement with a published number as **a question, not a verdict** — the first hypothesis is that a different quantity was computed. This rule binds its own citations: figures quoted in a ruling are verified against the tree before they enter this document, and where they cannot be found the verified figure is used and the substitution is stated. That clause is why the third occurrence above is a `PASS`/`FAIL` tally rather than the instance the ruling named: a #65 correction said to have taken its Sgemm gains from the wrong row does not survive the check — those figures were right as rate deltas and merely not the quantity the table published — while a genuine third arrived independently, from the same author, in the same session.

## 6. Known risks & standing orders

| Risk | Standing order |
|---|---|
| simd API churn (1.26→1.27 already broke) | All imports in `internal/vec`; on toolchain bump, fix the shim only, rerun differential tests |

| Bounds checks / write barriers in K-loop | `ssa/check_bce` in the spill-audit run; pointer-free kernel data |
| Perf numbers flattering on one machine | Bench harness records CPU model, frequency governor, and the host's *measured* peak alongside every result (§4/P2) |
| A wrong percent-of-peak denominator | Peak is measured by a register-only FMA-saturation kernel whose accumulator chains are verified to survive compilation (arithmetic witness) and whose loop is verified free of memory operands (disassembly); the formula is a printed cross-check only |
