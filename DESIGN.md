# keel — a float32 BLAS subset in pure Go on `GOEXPERIMENT=simd`

*Design document and Claude Code build plan. Working name "keel" (the foundation member of a hull) — rename at will.*

---

## 1. Mission

A pure-Go, cgo-free float32 BLAS subset whose hot kernels are written against the experimental `simd` / `simd/archsimd` packages (Go 1.26+, `GOEXPERIMENT=simd`). Target: ≥70% of single-threaded OpenBLAS SGEMM on AVX-512 hardware, with kernels that inline, respect safepoints, and parallelize on the caller's `GOMAXPROCS` via goroutines.

**Why it wins if it works:** preemption-safe, GC-friendly, deploys as a normal Go module, composes with the host application's scheduler. cgo-OpenBLAS can match the FLOPS but structurally cannot tell that story.

**Non-goals (v0):** float64 (Gonum owns it), complex types, full BLAS coverage, banded/packed storage, ARM64 (later; the architecture must make it a second microkernel, not a second library), float16 (no element type exists in the simd packages).

## 2. Scope: 15 routines, one keystone

| Level | Routines | Notes |
|---|---|---|
| 1 | `Sdot, Saxpy, Sscal, Snrm2, Sasum, Isamax` | Warm-up; validates shim + test harness |
| 2 | `Sgemv, Sger` | One packing dimension; rehearsal for L3 |
| 3 core | **`Sgemm`** | The keystone. All effort concentrates here |
| 3 derived | `Ssyrk, Strsm, Ssymm` | Blocked-GEMM + small corner kernels (BLIS decomposition) |

Row-major only in the public API (`float32` slices + explicit `ld` strides), matching Go idiom rather than Fortran heritage. Transpose flags supported; the packing routines absorb them for free.

## 3. Architecture

```
keel/
  keel.go              // public API: Sgemm(m,n,k, alpha, a, lda, b, ldb, beta, c, ldc) etc.
  dispatch.go          // runtime feature detect → avx512 / avx2 / scalar path
  internal/vec/        // THE SHIM. All simd/archsimd imports live here and only here.
    vec_avx512.go      //   //go:build goexperiment.simd && amd64
    vec_avx2.go
    vec_scalar.go      //   pure Go; always compiles; the semantic reference
  internal/kern/       // microkernels (straight-line, one intrinsic per op)
    sgemm_16x4_avx512.go
    sgemm_8x6_avx2.go
    sgemm_scalar.go
  internal/pack/       // panel packing (A: MC×KC col-panels; B: KC×NC row-panels)
  internal/block/      // Goto/BLIS loop nest (NC → KC → MC → NR → MR → microkernel)
  internal/oracle/     // float64 reference implementations for every routine
  internal/spill/      // spill-audit tooling (§6)
  bench/               // benchmark harness + optional cgo OpenBLAS reference (dev-only, build-tagged)
```

**The shim is load-bearing.** The simd API broke between 1.26 and 1.27 and will break again before graduation. Every intrinsic keel uses gets one wrapper in `internal/vec` (`Load16`, `Store16`, `FMA`, `Broadcast`, `HSum`, `MaskLoad`…). API churn is absorbed in one directory; kernels never import `simd` directly. The scalar implementation of the shim is the executable spec — every vector op has a scalar twin, and differential tests hold them equal.

## 4. Phases and gates

Every phase ends in an executable gate: a command that exits 0 or 1. No narrative "it works" — the gate script decides. Commit at every green gate.

### Phase 0 — Toolchain probe & shim (≈1 session)
- Install Go 1.27rc (or latest 1.26.x), verify `GOEXPERIMENT=simd go build` with a `//go:build goexperiment.simd` file importing `simd/archsimd` compiles and runs `X86.AVX512()` detection.
- Build `internal/vec` with the ~12 ops SGEMM needs, all three backends.
- **CRITICAL — read, don't recall:** run `go doc simd/archsimd` and read the package source under `$(go env GOROOT)/src/simd/` before writing any wrapper. The API is weeks old, has already had breaking renames, and any remembered function names are presumptively wrong. Copy exact identifiers from `go doc` output into the shim.
- Differential-test every vector op against its scalar twin on random + edge inputs (NaN, ±Inf, denormals, -0).
- **Gate P0:** shim tests pass under all three backends; `FMA` disassembles to a single `VFMADD231PS` (grep `-gcflags=-S` output). If no fused op exists in the current API, stop and surface it — mul+add is a half-of-peak ceiling and changes the target math.

### Phase 1 — Level 1 + test harness (≈1 session)
- Implement the six L1 routines on the shim; oracle versions in float64.
- Tolerance model (used everywhere): `|keel − oracle| ≤ C·f(n)·ε₃₂·scale`, with `f(n)=n` for dot-like reductions, `C≈4` slack for FMA/reassociation differences. Encode as one helper; never hand-pick per-test epsilons.
- Property tests: aliasing (`Saxpy(a, x, x)`), zero-length, stride ≠ 1, NaN propagation per BLAS convention.
- **Gate P1:** all L1 tests green on avx512 + scalar; benchmarks show ≥4× scalar for `Sdot` at n=4096.

### Phase 2 — Microkernel + spill audit (THE go/no-go, ≈1–2 sessions)
- Write `sgemm_32x6_avx512.go`. Tile choice: with 16-lane `Float32x16` vectors along M, a 16×4 tile gives only 4 accumulators — too few to hide FMA latency (~4-cycle latency × 2 ports wants ≥8–10 independent chains). Start at **MR=32, NR=6**: 2 vectors along M × 6 columns = **12 accumulators** + 2 A-registers + 1 B-broadcast = 15 live zmm, comfortable for the allocator. If the spill audit stays clean, grow toward MR=32, NR=12 (24 accumulators + 3 = 27 live zmm, near the practical ceiling); grow until spills appear, back off one step, record the frontier in `KERNEL.md`.
- Kernel-shaping rules: pre-slice packed panels to exact length outside the loop (bounds-check elimination — verify with `-gcflags=-d=ssa/check_bce`), pointer-free data (float32 slices ⇒ no write barriers), no function calls inside the K-loop, K-loop unrolled ×4.
- **Spill audit tooling** (`internal/spill`): a small Go program that runs `go build -gcflags=-S` on the kernel package and counts vector stores/loads to stack-relative addresses inside the K-loop body. Also emit `GOSSAFUNC=Kernel32x6 go build` and archive `ssa.html` per commit for human/CC inspection of *why* any spill happened.
- **Gate P2:** `spill-audit` reports **0 accumulator spills** in the steady-state K-loop, AND the raw microkernel (packed inputs, no blocking) clears the **throughput floor defined below**. If either fails after kernel-shaping and one shrink step: STOP, write `docs/spill-report.md` with the ssa.html evidence, and surface the decision (file upstream vs. avo fallback vs. accept AVX2 shapes). Do not silently proceed to Phase 3 on a broken kernel.
- **The throughput floor is roofline-relative on issue-bound hosts** (amended 2026-08-11, ruling on issue #19; supersedes the flat "≥55% of measured peak" for those hosts only). The original criterion has one denominator, the host's measured FMA peak, and so silently assumes the front end can *deliver* the kernel's instruction mix at 55% of that peak. On a host that retires two full-width FMAs per cycle from a ~4-wide front end, it cannot: the instruction budget is `issue_rate ÷ (FMA_rate × insns_per_FMA)` and it caps the achievable fraction *below the floor*, before a single cycle is wasted. Measured on janus.local (i9-9960X): 4.37 insns/cycle ÷ (1.944 FMA/cycle × 4.625 insns/FMA) = **48.6% is the ceiling**, and the kernel measured 46.0% — 94.6% of what the instruction set as-lowered can express (46.1%/94.8% on an independent run an hour earlier; `KERNEL.md` §7 records the agreement). Demanding 55% there is demanding the kernel beat the decode stage. The floor is therefore:
  - **FMA-bound host → ≥55% of measured peak, unchanged.** This is the default and the common case.
  - **Issue-bound host → ≥90% of its issue roofline**, where the roofline is `r_max ÷ (R × I)` with `r_max` the host's measured issue ceiling, `R` its measured FMA/cycle, and `I` the **spill-audit's own counted instructions per FMA** for the shape being measured. Same 55% intent, expressed against what the lowering can express rather than against a number the front end forbids.
  - The roofline is **clock-free**, so the gate needs no `taskset`, no `perf` counters and no frequency measurement. With `f_i` the measured fraction of peak for mix *i*, the observed retirement rate is `r_i = f_i · R · I_i`, and `R` is common to every mix on a host, so it cancels from both the classifier (a ratio of rates) and the roofline: **`roofline(I) = maxᵢ(f_i · I_i) / I`**. Rates below are quoted in insns/cycle for legibility, but nothing in the gate reads a clock.
  - `r_max` is the **maximum** rate observed across the ceiling mixes, not the mean. A ceiling is an upper bound on what was observed, and taking the max raises the roofline and so tightens the criterion — on janus, max 4.37 gives a 48.6% roofline and 94.6% attainment where the mean 4.33 would have given 48.1% and 95.6%. The stricter reading is the one a gate should take, and the classifier's 10% convergence requirement already bounds how far max and mean can diverge.
- **A host is classified issue-bound by evidence independent of the fraction being gated.** This matters: the naive test — "measured issue rate < the rate 55% would require" — expands to `f·R·I < 0.55·R·I`, i.e. `f < 0.55`, which is just "the host failed the floor" wearing a derivation. It would make the amendment self-granting. The real test is whether an issue *ceiling* exists at all, which only structurally different instruction mixes can show: a host is issue-bound iff the retirement rates of its **ceiling mixes** agree within 10% while their audited insns/FMA differ by ≥25%. Convergence across mixes is a property of the machine; divergence means something other than issue width binds. Cross-checked by the clock-free inverse-throughput test (two shapes' throughputs stand in the inverse ratio of their instruction counts: janus 1.308 against 1.351 predicted, a 3% miss; vesta 0.957 and antares 0.828, 29% and 39% off).
- **The ceiling mixes exclude the shape being gated, or the roofline floor decides nothing.** Write `p_i = f_i · I_i` and let *b* be the shape under test. Then `attain = f_b ÷ (maxᵢ p_i / I_b) = p_b / maxᵢ p_i`, so if *b* is itself one of the mixes, `attain ≥ minᵢ p_i / maxᵢ p_i = 1/cspread ≥ 1/1.10 = 0.909` — already above the 0.90 floor, **as an algebraic identity**. Every host the classifier admitted would clear the floor by construction, and worst of all in the binding case: on janus the shape under test *is* the argmin of `p_i`, so `1/cspread` and attainment agree to four places (0.9476). The ceiling is therefore established by the *other* mixes — the alternate shipped shape plus the register-only peak kernel — and *b* is then judged against it, which makes the two tests independent measurements. The first implementation of this gate had exactly this hole; the derivation above is why `scripts/roofline.sh` is a separate, unit-tested pure function rather than inline gate logic.
- **A ceiling the machine exceeds is not a ceiling.** Excluding *b* invites the mirror abuse — understate the ceiling and any *b* clears it — so two things bound it. The peak kernel is always a ceiling mix with `f = 1` by definition, pinning `maxᵢ p_i ≥ I_peak` no matter what the alternates do, which means sandbagging an alternate *breaks convergence* rather than lowering the roofline. And if `attain > 1`, the issue-bound hypothesis is falsified by the very data offered in its support and the host reverts to the flat floor. This is not hypothetical: **antares (Zen 5) is returned to the FMA-bound branch by exactly this clause.** Its ceiling mixes converge to within 9.1% (2×32 and the peak kernel) over a 2.06× mix spread, which would classify it issue-bound with a 39.3% roofline — but its winning 4×32 shape retires **158.5% of that roofline**, 58% *above* the ceiling those mixes set, and 63% above it at the median before the confidence interval is deducted. No ceiling, no roofline: it faces the flat 55% and clears it at 62.3% net of CI.
- **The roofline branch carries an anti-vacuity guard, without which it is not a gate.** A roofline computed from the instruction count of the kernel under test rises as that kernel gets worse: pad the loop with a hundred dead instructions and it still scores ~100% of its now-terrible roofline. So on the issue-bound branch the shape must *additionally* be within 5% of the best zero-spill insns/FMA in the recorded shape sweep (`KERNEL.md` §3). The shipped 2×32 is at 4.625 against a sweep best of 4.438 — 4.2% over, inside the guard. This is what keeps "≥90% of roofline" from meaning "≥90% of whatever we happened to emit"; a +40-instruction padded 2×32 scores 94.7% of its self-inflated roofline and is refused. Note also that the classifier resists gaming in the same direction: a merely-slow kernel produces *divergent* rates across shapes, lands in the FMA-bound branch, and faces the full 55%.
- **What the amendment costs, as a number.** Because the peak kernel pins `maxᵢ p_i ≥ I_peak` and the shape guard caps the denominator at `sweep_best × 1.05`, the effective floor for an issue-bound host is never below `0.90 × 2.25 ÷ 4.659 = 43.5% of measured peak`. That is the entire slack the amendment grants: from 55% to no less than 43.5%, and only to a host that has independently demonstrated a front-end ceiling it does not itself exceed. "Never a number without its denominator" applies to the gate's own leniency.
- **The claims above are tested, not asserted.** The decision is a pure function, `throughput_verdict` in `scripts/roofline.sh`, and `scripts/roofline-test.sh` drives it with fixtures that attempt each abuse: a +40-instruction padded kernel, a merely-slow kernel on a wide host, a sandbagged alternate shape, a single-mix ceiling set, an issue-bound host at 75% of its roofline, and both threshold boundaries. Those controls run at the **top** of `gate-p2.sh`, before any benchmarking, because a decision function that admits a padded kernel would make every number after it meaningless.
- **Cause of the roofline, and the standing task to retire it.** The roofline is not a fact about the ISA; it is a fact about this lowering. Go's assembler already encodes the instruction a hand-written SGEMM K-loop wants — `VFMADD231PS.BCST 12(SI), Z1, Z0`, verified assembling to `vfmadd231ps 12(%rsi){1to16}, %zmm1, %zmm0` — which accumulates in place and takes a broadcast memory multiplicand, collapsing four instructions into one. The intrinsic layer cannot reach it for three separate reasons (`docs/toolchain-notes.md` T12, issues #17/#18/#20, filed upstream as golang/go#80828, #80829 and #80830): only the 213 FMA form has an SSA op, so accumulation cannot land in the accumulator; the load-merge rule that *does* exist folds memory into the 213 form's addend, which in a GEMM is the accumulator and the one operand that must stay in a register; and no SSA op or rule anywhere emits the `.BCST` suffix the assembler supports. **Standing task:** when a toolchain lowers `MulAdd` to a 231-shaped FMA with a folded broadcast operand, re-audit and re-measure janus. The shipped 2×32 body goes 74 → ~46 instructions and `I` goes 4.625 → ~2.875. Note that **231 alone is not enough**: folding the accumulate but not the broadcast leaves 66 instructions and `I = 4.125`, which projects janus to ~51.7% of peak — past the 49.1% its ratcheted roofline floor would then demand, but still under the flat 55%, so the host would remain issue-bound. The embedded broadcast is the larger of the two levers, and only both together put janus over the flat floor.
- **The amendment ratchets; it does not retire.** An earlier draft of this section claimed it was self-retiring — that once the lowering improved, janus would stop classifying issue-bound and the flat floor would resume. The arithmetic says otherwise, and says something better. The effective floor is `0.90 × maxᵢ p_i ÷ I_b`, and `maxᵢ p_i` is pinned by the peak kernel, so the floor is **monotone non-increasing in `I_b`**: every improvement to the lowering *tightens* this gate automatically. Post-fix janus stays at its front-end ceiling, but its roofline rises to `2.250 ÷ 2.875 = 78.3%` and its required floor to `0.90 × 78.3% = 70.4%` — stricter than the 55% the amendment replaced, and cleared by the projected ~74%. A post-fix kernel at 60% of peak would pass the flat 55% and **fail** the ratchet; that is a control in `scripts/roofline-test.sh`. So the amendment needs no expiry clause and grants no permanent dispensation: it is exactly as strict as the instruction set as-lowered permits, and it follows the toolchain up.
- **Peak is measured, not derived** (revised 2026-08-11, decision on issue #11). The original formula — cores·freq·2 FMA ports·16 lanes·2 flops — assumes two full-width 512-bit FMA units. Zen 4 has none: it double-pumps AVX-512 over 256-bit datapaths and retires one 512-bit FMA per cycle, so the formula overstates that host's ceiling by 2× and would turn a 55% floor into a demand for ~110% of the silicon. The denominator is instead `BenchmarkPeak` in `bench/`: `internal/vec`'s register-only FMA-saturation kernels (no memory in the loop, ≥8 independent accumulator chains, distinct chain starts so CSE cannot merge them), measured per host under the §5.4 methodology. The formula survives as a **printed cross-check only**; a measured/formula divergence of ≥1.5× is the double-pump signature and is reported as expected rather than as a fault. This keeps the 55% floor meaningful — it is 55% of what the machine demonstrably does — without hardcoding a microarchitecture table, and it carries to Zen 5 and to a future arm64 port unchanged.

### Phase 3 — Packing + blocking → full SGEMM (≈2 sessions)
- Goto three-level blocking: NC (B panel → L3), KC (depth → L2 residency of A panel), MC (A panel → L2), then MR×NR microkernel over L1. Initial params for a Zen4/Ice Lake-class target: KC=384, MC=144 (multiple of MR), NC=4096 (multiple of NR); make them vars, auto-tune later.
- Packing routines SIMD-accelerated through the shim; transpose flags handled here.
- Edge kernels: masked loads/stores for M%MR, N%NR remainders (the simd API's mask support determines whether this is masked ops or a scalar fringe — read the API, then choose; scalar fringe is acceptable at these sizes).
- Beta handling (β=0 ⇒ no C read; β=1 ⇒ no multiply) as kernel variants, not branches in the loop.
- **Gate P3:** full `Sgemm` matches oracle across a size sweep (1..17, 63,64,65, 500, 1000, 2048, plus transpose/beta/alpha combinations); single-thread ≥60% of OpenBLAS at 2048³ (bench harness pulls OpenBLAS via build-tagged cgo, dev machine only, never a package dependency).
- **The reference is same-host OpenBLAS, on every gate host** (amended 2026-08-11, ruling on the provisioning question; issue #23). OpenBLAS is installed on all three amd64 gate hosts and the ratio is evaluated per host against *that host's own* OpenBLAS, in the same benchmark invocation. No cross-host reference and no designated golden machine: the only apples-to-apples ratio is same silicon, same thread count, same run — §7 rule 7 with no exception carved for convenience. The dev host stays what `docs/hosts.md` argues it is, plumbing verification only; its Homebrew OpenBLAS dispatches to the M4's matrix unit (`vortexm4`, ~1410 GFLOP/s from one thread, ~10× what that core's NEON FMA pipes can issue) and answers a different question than the gate asks.
- **The reference's own configuration is provenance, and the gate refuses a flattering one.** OpenBLAS version and the DYNAMIC_ARCH-selected kernel name are recorded beside every ratio, and `OPENBLAS_NUM_THREADS=1`/`OMP_NUM_THREADS=1` enforcement is both applied and *verified* from the library's own `openblas_get_num_threads()`. A distro package that quietly selects a pre-AVX2 kernel on an AVX-512 host reads low, which inflates keel's ratio — the one direction a gate must never fail in — so the selected kernel must be an AVX2-or-better µarch target or the criterion fails. An unrecognized new target name also fails, loudly: missing knowledge should cost a human a minute, not silently widen a bar.
- **On an issue-bound host the P3 denominator is `min(same-host OpenBLAS, roofline × measured peak)`** (same ruling; cause is #17/#18, `docs/toolchain-notes.md` T12). OpenBLAS on Skylake-X is hand assembly whose K-loop folds accumulation and an embedded broadcast into single FMAs — instructions the intrinsic layer provably cannot emit — so it lives *above* the front-end ceiling that caps keel's kernels. Asking keel for ≥60% of that is asking the decode stage, not the kernel, and P2 already adjudicated that root cause rather than leaving it as keel's defect. So keel is asked for ≥60% of what its instruction stream *as-lowered* can express. Four properties keep this from being a dispensation:
  - **It only ever lowers the denominator, and only for a host that independently demonstrated a front-end ceiling** by the P2 classifier (ceiling mixes converging within 10% over a ≥25% mix spread, the shape under test not exceeding the ceiling it sets). FMA-bound hosts are untouched: vesta and antares face the plain, unmodified criterion, so at least one host measures the comparison with no assistance at all.
  - **The roofline is the one belonging to the shape `Sgemm` actually ran**, read from the `keel-bench-kern` marker of the very run that produced the ratio, and it carries P2's anti-vacuity shape guard unchanged: a shape more than 5% above the sweep's best zero-spill insns/FMA is refused a roofline outright and the host reverts to the plain OpenBLAS denominator. A fatter kernel cannot buy itself a lower bar — which is not hypothetical here: the guard refused the then-dispatched 4×32 (6.250 insns/FMA against a 4.438 sweep best) while only the 2×32 the sentinel gated (4.625) was inside it, and that red is what surfaced issue #24. Dispatch was shipping a shape janus demonstrably should not run, and the guard declined to paper over it with a forgiving roofline; the fix was the dispatch bug, not the guard, and the next bullet is the ruling.
  - **It ratchets exactly as P2's floor does.** The roofline term is `maxᵢ p_i / I`, monotone in the gated shape's instruction count, so every improvement to the lowering raises it; when it rises above same-host OpenBLAS the `min` picks OpenBLAS and the amendment retires itself with no expiry clause to remember. Same standing task as §4/P2: when a toolchain lowers `MulAdd` to a 231-shaped FMA with a folded broadcast, re-audit and re-measure janus, which then reverts to the plain reference.
  - **Both ratios are always printed**, amended and plain, on every host. The gate's leniency is itself a number with a denominator; hiding the unassisted figure would be the reporting failure §7 rule 7 exists to prevent.
- **Microkernel shape is selected per host, by the same issue-bound/FMA-bound classification** (amended 2026-08-11, ruling on issue #24). P2 shipped two zero-spill shapes and `KERNEL.md` §7 measured the winner flipping between them: 4×32 on Zen 4 and Zen 5, 2×32 on Skylake-X by 11 percentage points. Dispatch took the registry's first entry, so it ran 4×32 everywhere — a performance bug on one of three hosts, and the one the roofline guard then refused. So `Sgemm` now classifies the host and picks the shape extremal on that class's binding cost: an FMA-bound host takes the fewest memory ops per FMA (4×32, 0.75), an issue-bound host the fewest instructions per FMA (2×32, 4.625). This is not a weakening; per-target microkernel shapes are what BLIS and OpenBLAS both carry, "one shape everywhere" was never a principle here, and P2's own data proved the physics — on janus the two shapes' throughputs stand in the inverse ratio of their instruction counts. Three properties keep it honest, and `KERNEL.md` §8 is the record:
  - **The gate requires that the shape measured is the shape dispatch selects.** The throughput sentinel judges the dispatched shape rather than whichever shipped shape measures fastest — with a per-host choice those stopped being the same claim — and the other shapes become its ceiling set. Both are benchmarked in one invocation, so "did dispatch pick the faster one" is answered from the same measurement: if a passed-over shape's lower bound clears the dispatched shape's point estimate, the gate fails. The blocked `Sgemm` at 2048³ is then re-measured with `KEEL_KERN_CLASS` pinned to the other class, as a cross-check on the number the criterion actually rests on.
  - **The classification is a proxy, so it is checked against measurement on every host, every run.** `archsimd` reports CPU features and never a vendor, family or model, and `internal/cpu` discards the CPUID signature word, so no microarchitecture is readable from pure Go here (`docs/toolchain-notes.md` T14, issue #25). `kern.HostClass` fingerprints the generation from a feature bundle instead — AVX-512 with VBMI2+VPOPCNTDQ is Ice Lake / Zen 4 or later — and the library prints its verdict and its grounds so the gate can compare them against the class its own convergence test derives from the measurements. Disagreement is a gate failure. Neither error direction can make a gate lenient: a wrongly-FMA-bound host dispatches the fat shape, which the roofline guard then refuses, making the bar *stricter*; a wrongly-issue-bound host gives up throughput, which the same-invocation shape comparison catches.
  - **The instruction counts the ranking reads are re-derived from the object code.** `Kernel.InsnsPerFMA` is a measurement recorded in Go source, and it decides what ships, so the gate recounts every shipped shape's loop body in the spill audit and fails on disagreement. An unaudited shape is unrankable rather than lean, which is a second lock on the spilling reference tile never being selected.
- **One re-run for a failing sentinel reading, and the retry is part of the record** (added 2026-08-11 by ruling, recorded on issue #4; this is an allowance granted to the gate model, not one the implementer may grant itself). A *throughput sentinel* criterion — P2's ≥55% floor, and its P3 successor requiring ≥90% of the dispatched shape's roofline on an issue-bound host — that reads as failing triggers exactly one immediate re-run; the criterion fails only if **both** runs fail. **Both outputs are archived in the gate record either way** (the session-end comment on the phase umbrella issue, pasted verbatim per `CLAUDE.md`), so a gate that passed on the second reading visibly says that it did, and a run of retries would be legible as one. This is a statistical allowance, not a mulligan: one retry, never a loop, and **never applicable to a correctness criterion** — oracle sweeps, differential tests, spill/call/BCE audits and the shape-agreement checks fail on first miss, because a differential test that passes on retry has found a nondeterminism worth more attention than the gate colour, not less.
  - It exists because janus's roofline attainment is the tightest margin in the gate and the only criterion whose ordinary variance can straddle its bar: two independent runs an hour apart read 95.0% and 93.7% against ≥90%. Writing that down converts a future fire drill into a documented allowance; leaving it as an operator's instinct is how "re-run once" decays into "re-run until green".
  - `scripts/gate-p3.sh` itself is unchanged and still fails on the first miss — the allowance is the operator's, and the archive is what keeps it honest. A gate that retried internally would have to be trusted to report that it had; a human re-run that must paste both outputs into the umbrella issue is auditable by construction.

### Phase 4 — Level 2 + derived Level 3 (≈2 sessions)
- `Sgemv` (both transposes), `Sger`.
- `Ssyrk`, `Ssymm` as blocked GEMM with triangular masking in the C-update; `Strsm` as small unblocked triangular solves at the diagonal + GEMM rank-updates elsewhere (the BLIS recipe — cite it in code comments so future readers know the shape is standard).
- **Gate P4:** all routines green vs oracle incl. upper/lower × trans × unit-diag lattice for `Strsm`; `Ssyrk` ≥85% of `Sgemm` GFLOPS at same size.

### Phase 5 — Parallelism, dispatch, polish (≈1–2 sessions)
- Parallelize the MC (ic) loop over a bounded worker pool sized by `runtime.GOMAXPROCS(0)`; shared packed-B panel per NC iteration, per-worker packed-A buffers from a `sync.Pool`. No background threads, no state between calls.
- Runtime dispatch finalized: `avx512 → avx2 → scalar`, overridable by env `KEEL_FORCE=scalar` for testing.
- The package must compile and pass (scalar path) *without* `GOEXPERIMENT=simd` — build tags make the fast paths additive. This is what lets it exist on proper `go get` terms the day the experiment graduates.
- Scaling benchmark, README with honest numbers, `doc.go`.
- **Named input carried in from P3: close janus's retention gap (issue #26), don't regress the Zens** (added 2026-08-11). This is the "make them vars, auto-tune later" half of P3's blocking work coming due. ## 5. Testing philosophy (for the whole project)

1. **Oracle-driven:** float64 reference for every routine; the tolerance helper is the only place epsilons live.
2. **Differential across backends:** avx512 vs avx2 vs scalar on identical inputs must agree within reassociation tolerance — catches shim bugs independent of the oracle.
3. **Adversarial shapes first-class:** every dimension in {0,1,MR−1,MR,MR+1,…}; strides > width; overlapping aliases where BLAS defines behavior.
4. **Benchmarks are tests:** perf gates run in CI-mode locally (`go test -run=NONE -bench=Gate`) and the gate script parses the numbers. A silent 2× regression should fail a gate, not await a human.
5. **Gate benchmark methodology** (revised 2026-08-11, decision on issue #14): `-count=10 -benchtime=1s`, at least one measuring host under the `performance` governor, aggregated by `benchstat` (pinned as a module tool, so the version is in the repo). The gate compares **medians**, and a threshold counts as cleared only if it is cleared **net of benchstat's reported confidence interval** — numerator down by its CI, denominator up by its own. A distribution too wide for benchstat to bound is a failure to measure, not a pass. `-benchtime=3x` remains acceptable for smoke runs that inform no gate. Rationale: P1's first ratios came from `-benchtime=3x -count=5` reduced by min-of-samples, whose raw samples spread by 3.08× inside a single backend; ten one-second runs collapse that to low single-digit percent, and "clear the bar net of CI" means no gate can go green on a lucky run. Mechanics live in `scripts/bench.sh`, shared by every gate so none can quietly deviate.

## 6. Known risks & standing orders

| Risk | Standing order |
|---|---|
| simd API churn (1.26→1.27 already broke) | All imports in `internal/vec`; on toolchain bump, fix the shim only, rerun differential tests |
| Register allocator spills accumulators | Phase 2 gate + shrink protocol; never work around silently; produce `spill-report.md` with ssa.html |
| No FMA intrinsic / wrong lowering | Phase 0 gate; disassembly grep is the arbiter, not the doc comment |
| CC hallucinating the archsimd API | Mandatory `go doc` + GOROOT source read before shim edits; identifiers copied, never recalled |
| Bounds checks / write barriers in K-loop | `ssa/check_bce` in the spill-audit run; pointer-free kernel data |
| Perf numbers flattering on one machine | Bench harness records CPU model, frequency governor, and the host's *measured* peak alongside every result (§4/P2) |
| A wrong percent-of-peak denominator | Peak is measured by a register-only FMA-saturation kernel whose accumulator chains are verified to survive compilation (arithmetic witness) and whose loop is verified free of memory operands (disassembly); the formula is a printed cross-check only |
