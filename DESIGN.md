# keel — a float32 BLAS subset in pure Go on `GOEXPERIMENT=simd`

*Design document and Claude Code build plan. Working name "keel" (the foundation member of a hull) — rename at will.*

---

## 1. Mission

A pure-Go, cgo-free float32 BLAS subset whose hot kernels are written against the experimental `simd` / `simd/archsimd` packages (Go 1.26+, `GOEXPERIMENT=simd`). Target: ≥70% of single-threaded OpenBLAS SGEMM on AVX-512 hardware, with kernels that inline, respect safepoints, and parallelize on the caller's `GOMAXPROCS` via goroutines.

**Why it wins if it works:** preemption-safe, GC-friendly, deploys as a normal Go module, composes with the host application's scheduler. cgo-OpenBLAS can match the FLOPS but structurally cannot tell that story.

**Non-goals (v0):** float64 (Gonum owns it), complex types, full BLAS coverage, banded/packed storage, ARM64 (later; the architecture must make it a second microkernel, not a second library), float16 (no element type exists in the simd packages).

## 2. Scope: 12 routines, one keystone

| Level | Routines | Notes |
|---|---|---|
| 1 | `Sdot, Saxpy, Sscal, Snrm2, Sasum, Isamax` | Warm-up; validates shim + test harness |
| 2 | `Sgemv, Sger` | One packing dimension; rehearsal for L3 |
| 3 core | **`Sgemm`** | The keystone. All effort concentrates here |
| 3 derived | `Ssyrk, Strsm, Ssymm` | Blocked-GEMM + small corner kernels (BLIS decomposition) |

Row-major only in the public API (`float32` slices + explicit `ld` strides), matching Go idiom rather than Fortran heritage. Transpose flags supported; the packing routines absorb them for free.

## 3. Architecture

```
keel/
  keel.go              // public API: Sgemm(m,n,k, alpha, a, lda, b, ldb, beta, c, ldc) etc.
  dispatch.go          // runtime feature detect: L1 avx512/avx2/scalar, L3 avx512/scalar (#40)
  internal/vec/        // THE SHIM. All simd/archsimd imports live here and only here.
    vec_avx512.go      //   //go:build goexperiment.simd && amd64
    vec_avx2.go
    vec_scalar.go      //   pure Go; always compiles; the semantic reference
  internal/kern/       // microkernels (straight-line, one intrinsic per op)
    sgemm_16x4_avx512.go
    sgemm_8x6_avx2.go
    sgemm_scalar.go
  internal/pack/       // panel packing (A: MC×KC col-panels; B: KC×NC row-panels)
  internal/block/      // Goto/BLIS loop nest (NC → KC → MC → NR → MR → microkernel)
  internal/oracle/     // float64 reference implementations for every routine
  internal/spill/      // spill-audit tooling (§6)
  bench/               // benchmark harness + optional cgo OpenBLAS reference (dev-only, build-tagged)
```

**The shim is load-bearing.** The simd API broke between 1.26 and 1.27 and will break again before graduation. Every intrinsic keel uses gets one wrapper in `internal/vec` (`Load16`, `Store16`, `FMA`, `Broadcast`, `HSum`, `MaskLoad`…). API churn is absorbed in one directory; kernels never import `simd` directly. The scalar implementation of the shim is the executable spec — every vector op has a scalar twin, and differential tests hold them equal.

## 4. Phases and gates

Every phase ends in an executable gate: a command that exits 0 or 1. No narrative "it works" — the gate script decides. Commit at every green gate.

### Phase 0 — Toolchain probe & shim (≈1 session)
- Install Go 1.27rc (or latest 1.26.x), verify `GOEXPERIMENT=simd go build` with a `//go:build goexperiment.simd` file importing `simd/archsimd` compiles and runs `X86.AVX512()` detection.
- Build `internal/vec` with the ~12 ops SGEMM needs, all three backends.
- **CRITICAL — read, don't recall:** run `go doc simd/archsimd` and read the package source under `$(go env GOROOT)/src/simd/` before writing any wrapper. The API is weeks old, has already had breaking renames, and any remembered function names are presumptively wrong. Copy exact identifiers from `go doc` output into the shim.
- Differential-test every vector op against its scalar twin on random + edge inputs (NaN, ±Inf, denormals, -0).
- **Gate P0:** shim tests pass under all three backends; `FMA` disassembles to **a single fused multiply-add instruction — any `VFMADD*PS` form — rather than a separate multiply and add** (grep `-gcflags=-S` output). If no fused op exists in the current API, stop and surface it: mul+add is a half-of-peak ceiling and changes the target math.
  - **The criterion is fusion, not an encoding** (reworded 2026-08-12, issue #10). This originally named `VFMADD231PS`, which is the form a hand-written K-loop wants and *not* what the compiler emits: go1.26.5 lowers `MulAdd` to `VFMADD213PS`, so the criterion as first written would have failed a toolchain that satisfied it. What P0 needs to establish is that one instruction does the multiply and the add with a single rounding, because that is what sets the achievable ceiling; which of the three operand orders carries it is a separate question with separate consequences, and it belongs where those consequences are — §"Cause of the roofline" below, where 231-vs-213 is the difference between `I = 4.625` and `I ≈ 2.875` and is tracked as a standing task against the lowering. Keeping the two apart means a criterion cannot be satisfied or failed by an encoding change that does not move the ceiling.

### Phase 1 — Level 1 + test harness (≈1 session)
- Implement the six L1 routines on the shim; oracle versions in float64.
- Tolerance model (used everywhere): `|keel − oracle| ≤ C·f(n)·ε₃₂·scale`, with `f(n)=n` for dot-like reductions, `C≈4` slack for FMA/reassociation differences. Encode as one helper; never hand-pick per-test epsilons.
- Property tests: aliasing (`Saxpy(a, x, x)`), zero-length, stride ≠ 1, NaN propagation per BLAS convention.
- **Gate P1:** all L1 tests green on avx512 + scalar; benchmarks show ≥4× scalar for `Sdot` at n=4096.

### Phase 2 — Microkernel + spill audit (THE go/no-go, ≈1–2 sessions)
- Write the AVX-512 microkernel (`internal/vec/gemm_amd64.go`). **Naming convention, stated here so no reader has to re-derive it: a tile written `MR`×`NR` is MR *rows* × NR *columns* of row-major C, and the 16-lane `Float32x16` vectors lie along N — along a row — because §3's public API is row-major.** Tile choice: a tile with only 4 accumulators cannot hide FMA latency (~4-cycle latency × 2 ports wants ≥8–10 independent chains). Start at **MR=6, NR=32**: 6 rows × 2 vectors along N = **12 accumulators** + 2 B-registers + 1 A-broadcast = 15 live zmm, comfortable for the allocator. If the spill audit stays clean, grow toward MR=12, NR=32 (24 accumulators + 3 = 27 live zmm, near the practical ceiling); grow until spills appear, back off one step, record the frontier in `KERNEL.md`.
  - **Amended 2026-08-16 by ruling on issue #16, and the amendment is to the doc, not to the code.** This line read **MR=32, NR=6** — "2 vectors along M × 6 columns" — from the first commit, and that was a **pre-implementation fossil in BLIS's column-major orientation**, written before §3's row-major decision had propagated through the design. There is **no intended column-major internal C**. Vectors along M in a row-major C put each accumulator's 16 elements `ldc` floats apart, on sixteen cache lines, so writing one tile out means 32×6 = 192 scalar stores, each needing a lane extract that `archsimd` can only perform by storing the vector to memory and reloading the element — *literally a spill*, in the very K-loop P2's spill audit exists to inspect. **The documented tile would have failed P2's own gate criterion by construction**, for a reason having nothing to do with the compiler under audit. Under the reflection every quantity the phase was designed to test is unchanged — 12 accumulators, 15 live zmm, the arithmetic, the FMA count per k-step — and only the axis names move, taking C's access pattern from strided-scalar to contiguous-vector with them. **The reflection fixes the orientation and leaves the plan's *prediction* falsified, which is worth saying rather than leaving a reader to notice.** The reflected 12-accumulator tile is exactly `Kernel6x32`, and it is **not** "comfortable for the allocator": it spills heavily (90 vector stack refs, 50 register copies, 5.62 insns per arith — `docs/spill-report.md` §"the other P2 finding", cause in T10/#18, only 15 of 32 vector registers allocatable). It is measured on every gate host and never dispatched — 30.5% of measured peak on Zen 4 against 96.6% for `Kernel4x32`. **What ships is smaller than what this line plans for**: `Kernel2x32` and `Kernel4x32`, at 4 and 8 accumulators. The sentence above is retained as the phase's plan, in the corrected orientation; the measured outcome is P2's headline finding and lives in `docs/spill-report.md` and `KERNEL.md` §3.
- Kernel-shaping rules: pre-slice packed panels to exact length outside the loop (bounds-check elimination — verify with `-gcflags=-d=ssa/check_bce`), pointer-free data (float32 slices ⇒ no write barriers), no function calls inside the K-loop, K-loop unrolled ×4.
- **Spill audit tooling** (`internal/spill`): a small Go program that runs `go build -gcflags=-S` on the kernel package and counts vector stores/loads to stack-relative addresses inside the K-loop body. Also emit `GOSSAFUNC=Kernel4x32 go build` and archive `ssa.html` per commit for human/CC inspection of *why* any spill happened.
- **Gate P2:** `spill-audit` reports **0 accumulator spills** in the steady-state K-loop, AND the raw microkernel (packed inputs, no blocking) clears the **throughput floor defined below**. If either fails after kernel-shaping and one shrink step: STOP, write `docs/spill-report.md` with the ssa.html evidence, and surface the decision (file upstream vs. avo fallback vs. accept AVX2 shapes). Do not silently proceed to Phase 3 on a broken kernel.
- **The throughput floor is roofline-relative on issue-bound hosts** (amended 2026-08-11, ruling on issue #19; supersedes the flat "≥55% of measured peak" for those hosts only). The original criterion has one denominator, the host's measured FMA peak, and so silently assumes the front end can *deliver* the kernel's instruction mix at 55% of that peak. On a host that retires two full-width FMAs per cycle from a ~4-wide front end, it cannot: the instruction budget is `issue_rate ÷ (FMA_rate × insns_per_FMA)` and it caps the achievable fraction *below the floor*, before a single cycle is wasted. Measured on janus (i9-9960X): 4.37 insns/cycle ÷ (1.944 FMA/cycle × 4.625 insns/FMA) = **48.6% is the ceiling**, and the kernel measured 46.0% — 94.6% of what the instruction set as-lowered can express (46.1%/94.8% on an independent run an hour earlier; `KERNEL.md` §7 records the agreement). Demanding 55% there is demanding the kernel beat the decode stage. The floor is therefore:
  - **FMA-bound host → ≥55% of measured peak, unchanged.** This is the default and the common case.
  - **Issue-bound host → ≥90% of its issue roofline**, where the roofline is `r_max ÷ (R × I)` with `r_max` the host's measured issue ceiling, `R` its measured FMA/cycle, and `I` the **spill-audit's own counted instructions per FMA** for the shape being measured. Same 55% intent, expressed against what the lowering can express rather than against a number the front end forbids.
  - The roofline is **clock-free**, so the gate needs no `taskset`, no `perf` counters and no frequency measurement. With `f_i` the measured fraction of peak for mix *i*, the observed retirement rate is `r_i = f_i · R · I_i`, and `R` is common to every mix on a host, so it cancels from both the classifier (a ratio of rates) and the roofline: **`roofline(I) = maxᵢ(f_i · I_i) / I`**. Rates below are quoted in insns/cycle for legibility, but nothing in the gate reads a clock.
  - `r_max` is the **maximum** rate observed across the ceiling mixes, not the mean. A ceiling is an upper bound on what was observed, and taking the max raises the roofline and so tightens the criterion — on janus, max 4.37 gives a 48.6% roofline and 94.6% attainment where the mean 4.33 would have given 48.1% and 95.6%. The stricter reading is the one a gate should take, and the classifier's 10% convergence requirement already bounds how far max and mean can diverge.
- **A host is classified issue-bound by evidence independent of the fraction being gated.** This matters: the naive test — "measured issue rate < the rate 55% would require" — expands to `f·R·I < 0.55·R·I`, i.e. `f < 0.55`, which is just "the host failed the floor" wearing a derivation. It would make the amendment self-granting. The real test is whether an issue *ceiling* exists at all, which only structurally different instruction mixes can show: a host is issue-bound iff the retirement rates of its **ceiling mixes** agree within 10% while their audited insns/FMA differ by ≥25%. Convergence across mixes is a property of the machine; divergence means something other than issue width binds. Cross-checked by the clock-free inverse-throughput test (two shapes' throughputs stand in the inverse ratio of their instruction counts: janus 1.308 against 1.351 predicted, a 3% miss; vesta 0.957 and antares 0.828, 29% and 39% off).
- **The ceiling mixes exclude the shape being gated, or the roofline floor decides nothing.** Write `p_i = f_i · I_i` and let *b* be the shape under test. Then `attain = f_b ÷ (maxᵢ p_i / I_b) = p_b / maxᵢ p_i`, so if *b* is itself one of the mixes, `attain ≥ minᵢ p_i / maxᵢ p_i = 1/cspread ≥ 1/1.10 = 0.909` — already above the 0.90 floor, **as an algebraic identity**. Every host the classifier admitted would clear the floor by construction, and worst of all in the binding case: on janus the shape under test *is* the argmin of `p_i`, so `1/cspread` and attainment agree to four places (0.9476). The ceiling is therefore established by the *other* mixes — the alternate shipped shape plus the register-only peak kernel — and *b* is then judged against it, which makes the two tests independent measurements. The first implementation of this gate had exactly this hole; the derivation above is why `scripts/roofline.sh` is a separate, unit-tested pure function rather than inline gate logic.
- **A ceiling the machine exceeds is not a ceiling.** Excluding *b* invites the mirror abuse — understate the ceiling and any *b* clears it — so two things bound it. The peak kernel is always a ceiling mix with `f = 1` by definition, pinning `maxᵢ p_i ≥ I_peak` no matter what the alternates do, which means sandbagging an alternate *breaks convergence* rather than lowering the roofline. And if `attain > 1`, the issue-bound hypothesis is falsified by the very data offered in its support and the host reverts to the flat floor. This is not hypothetical: **antares (Zen 5) is returned to the FMA-bound branch by exactly this clause.** Its ceiling mixes converge to within 9.1% (2×32 and the peak kernel) over a 2.06× mix spread, which would classify it issue-bound with a 39.3% roofline — but its winning 4×32 shape retires **158.5% of that roofline**, 58% *above* the ceiling those mixes set, and 63% above it at the median before the confidence interval is deducted. No ceiling, no roofline: it faces the flat 55% and clears it at 62.3% net of CI.
- **The roofline branch carries an anti-vacuity guard, without which it is not a gate.** A roofline computed from the instruction count of the kernel under test rises as that kernel gets worse: pad the loop with a hundred dead instructions and it still scores ~100% of its now-terrible roofline. So on the issue-bound branch the shape must *additionally* be within 5% of the best insns/FMA any *emittable* zero-spill shape reaches (`KERNEL.md` §3), re-derived from `tools/shapegen`'s enumeration on every gate run rather than read from a constant (#107). The shipped 2×32 is at 4.625 against a frontier of 4.625 — it *is* the frontier, ratio 1.000, so what the guard detects on this shape is drift off the frontier rather than distance from it. Corrected 2026-08-18 from a recorded sweep best of 4.438, which named a `Permute` shape needing 16 index vectors against T10's 15 registers and so could not be emitted at all. This is what keeps "≥90% of roofline" from meaning "≥90% of whatever we happened to emit"; a +40-instruction padded 2×32 scores 94.7% of its self-inflated roofline and is refused. Note also that the classifier resists gaming in the same direction: a merely-slow kernel produces *divergent* rates across shapes, lands in the FMA-bound branch, and faces the full 55%.
- **What the amendment costs, as a number.** Because the peak kernel pins `maxᵢ p_i ≥ I_peak` and the shape guard caps the denominator at `sweep_best × 1.05`, the effective floor for an issue-bound host is never below `0.90 × 2.25 ÷ 4.856 = 41.7% of measured peak` (4.659 = 43.5% until the 2026-08-18 correction of `sweep_best`; only the cap moved, and the floor the shipped 2×32 actually faces is unchanged at 43.8% because it is computed from that shape's own audited `I_b`). That is the entire slack the amendment grants: from 55% to no less than 41.7%, and only to a host that has independently demonstrated a front-end ceiling it does not itself exceed. "Never a number without its denominator" applies to the gate's own leniency.
- **The claims above are tested, not asserted.** The decision is a pure function, `throughput_verdict` in `scripts/roofline.sh`, and `scripts/roofline-test.sh` drives it with fixtures that attempt each abuse: a +40-instruction padded kernel, a merely-slow kernel on a wide host, a sandbagged alternate shape, a single-mix ceiling set, an issue-bound host at 75% of its roofline, and both threshold boundaries. Those controls run at the **top** of `gate-p2.sh`, before any benchmarking, because a decision function that admits a padded kernel would make every number after it meaningless.
- **Cause of the roofline, and the standing task to retire it.** The roofline is not a fact about the ISA; it is a fact about this lowering. Go's assembler already encodes the instruction a hand-written SGEMM K-loop wants — `VFMADD231PS.BCST 12(SI), Z1, Z0`, verified assembling to `vfmadd231ps 12(%rsi){1to16}, %zmm1, %zmm0` — which accumulates in place and takes a broadcast memory multiplicand, collapsing four instructions into one. The intrinsic layer cannot reach it for three separate reasons (`docs/toolchain-notes.md` T12, issues #17/#18/#20, filed upstream as golang/go#80828, #80829 and #80830): only the 213 FMA form has an SSA op, so accumulation cannot land in the accumulator; the load-merge rule that *does* exist folds memory into the 213 form's addend, which in a GEMM is the accumulator and the one operand that must stay in a register; and no SSA op or rule anywhere emits the `.BCST` suffix the assembler supports. **Standing task:** when a toolchain lowers `MulAdd` to a 231-shaped FMA with a folded broadcast operand, re-audit and re-measure janus. The shipped 2×32 body goes 74 → ~46 instructions and `I` goes 4.625 → ~2.875. Note that **231 alone is not enough**: folding the accumulate but not the broadcast leaves 66 instructions and `I = 4.125`, which projects janus to ~51.7% of peak — past the 49.1% its ratcheted roofline floor would then demand, but still under the flat 55%, so the host would remain issue-bound. The embedded broadcast is the larger of the two levers, and only both together put janus over the flat floor.
- **The amendment ratchets; it does not retire.** An earlier draft of this section claimed it was self-retiring — that once the lowering improved, janus would stop classifying issue-bound and the flat floor would resume. The arithmetic says otherwise, and says something better. The effective floor is `0.90 × maxᵢ p_i ÷ I_b`, and `maxᵢ p_i` is pinned by the peak kernel, so the floor is **monotone non-increasing in `I_b`**: every improvement to the lowering *tightens* this gate automatically. Post-fix janus stays at its front-end ceiling, but its roofline rises to `2.250 ÷ 2.875 = 78.3%` and its required floor to `0.90 × 78.3% = 70.4%` — stricter than the 55% the amendment replaced, and cleared by the projected ~74%. A post-fix kernel at 60% of peak would pass the flat 55% and **fail** the ratchet; that is a control in `scripts/roofline-test.sh`. So the amendment needs no expiry clause and grants no permanent dispensation: it is exactly as strict as the instruction set as-lowered permits, and it follows the toolchain up.
- **Peak is measured, not derived** (revised 2026-08-11, decision on issue #11). The original formula — cores·freq·2 FMA ports·16 lanes·2 flops — assumes two full-width 512-bit FMA units. Zen 4 has none: it double-pumps AVX-512 over 256-bit datapaths and retires one 512-bit FMA per cycle, so the formula overstates that host's ceiling by 2× and would turn a 55% floor into a demand for ~110% of the silicon. The denominator is instead `BenchmarkPeak` in `bench/`: `internal/vec`'s register-only FMA-saturation kernels (no memory in the loop, ≥8 independent accumulator chains, distinct chain starts so CSE cannot merge them), measured per host under the §5 rule 5 methodology. The formula survives as a **printed cross-check only**; a measured/formula divergence of ≥1.5× is the double-pump signature and is reported as expected rather than as a fault. This keeps the 55% floor meaningful — it is 55% of what the machine demonstrably does — without hardcoding a microarchitecture table, and it carries to Zen 5 and to a future arm64 port unchanged.

### Phase 3 — Packing + blocking → full SGEMM (≈2 sessions)
- Goto three-level blocking: NC (B panel → L3), KC (depth → L2 residency of A panel), MC (A panel → L2), then MR×NR microkernel over L1. Initial params for a Zen4/Ice Lake-class target: KC=384, MC=144 (multiple of MR), NC=4096 (multiple of NR); make them vars, auto-tune later.
- Packing routines SIMD-accelerated through the shim; transpose flags handled here.
- Edge kernels: masked loads/stores for M%MR, N%NR remainders (the simd API's mask support determines whether this is masked ops or a scalar fringe — read the API, then choose; scalar fringe is acceptable at these sizes).
- Beta handling (β=0 ⇒ no C read; β=1 ⇒ no multiply) as kernel variants, not branches in the loop.
- **Gate P3:** full `Sgemm` matches oracle across a size sweep (1..17, 63,64,65, 500, 1000, 2048, plus transpose/beta/alpha combinations); single-thread ≥60% of OpenBLAS at 2048³ (bench harness pulls OpenBLAS via build-tagged cgo, dev machine only, never a package dependency).
- **The reference is same-host OpenBLAS, on every gate host** (amended 2026-08-11, ruling on the provisioning question; issue #23). OpenBLAS is installed on all three amd64 gate hosts and the ratio is evaluated per host against *that host's own* OpenBLAS, in the same benchmark invocation. No cross-host reference and no designated golden machine: the only apples-to-apples ratio is same silicon, same thread count, same run — §7 rule 7 with no exception carved for convenience. The dev host stays what `docs/hosts.md` argues it is, plumbing verification only; its Homebrew OpenBLAS dispatches to the M4's matrix unit (`vortexm4`, ~1410 GFLOP/s from one thread, ~10× what that core's NEON FMA pipes can issue) and answers a different question than the gate asks.
- **The reference's own configuration is provenance, and the gate refuses a flattering one.** OpenBLAS version and the DYNAMIC_ARCH-selected kernel name are recorded beside every ratio, and `OPENBLAS_NUM_THREADS=1`/`OMP_NUM_THREADS=1` enforcement is both applied and *verified* from the library's own `openblas_get_num_threads()`. A distro package that quietly selects a pre-AVX2 kernel on an AVX-512 host reads low, which inflates keel's ratio — the one direction a gate must never fail in — so the selected kernel must be an AVX2-or-better µarch target or the criterion fails. An unrecognized new target name also fails, loudly: missing knowledge should cost a human a minute, not silently widen a bar.
- **The reference is the fastest *measured* same-host OpenBLAS over a coretype sweep, not whatever `DYNAMIC_ARCH` selected** (amended 2026-08-11, ruling on issue #31). Each host's reference is measured under `{default, Zen, Haswell, SkylakeX, Cooperlake, SapphireRapids}` forced through `OPENBLAS_CORETYPE`, best-of-N under §5 rule 5's methodology, and the fastest is pinned for the run that produces the ratio. **Every candidate's `corename` and rate is recorded in the provenance block, not just the winner**, and the pin is verified from the library's reported `corename` rather than trusted from the environment. The allowlist of the previous bullet keeps its narrowed job — the *floor*, "modern enough" — and the sweep supplies the *ceiling*, "the best this silicon can do". Why the change: `DYNAMIC_ARCH` dispatches on an ISA feature check, so on vesta's Zen 4 it ships a full-width Cooperlake kernel onto a double-pumped 256-bit datapath and the AVX2 `Haswell` kernel measures **6.7% faster** (159.5 vs 149.5 GFLOP/s), while antares (Zen 5, full-width) and janus (Skylake-X) both select correctly. That is keel's own #24 bug with the vendors reversed, and it means "whatever the library picked" delegates the denominator's one inviolable property — that it never flatters keel — to an upstream heuristic measured wrong on one of three hosts. Same move as #11's measured-peak ruling: measure the denominator instead of trusting a selector, which also needs no µarch table to maintain and survives every future host and OpenBLAS bump. This binds whether or not it changes a verdict: where the `min` of the next bullet makes it provenance-only, a provenance block recording a reference known to be 6.7% low is still a defect in the evidentiary record.
- **The performance governor is asserted on every host, not assumed** (same ruling). `gate-p3.sh`'s preamble and `provision-openblas.sh` both read `scaling_governor` per host and fail on anything but `performance`; unreadable counts as unmet, and the gate re-reads it at measurement time so a governor that changed after the preamble fails that host instead of passing on a stale check. The gate used to read it and only *label* the OpenBLAS pass line with it — a tally any single host could satisfy — which let antares measure on `powersave` — where its first OpenBLAS reading was 245.0 GFLOP/s against a 296–297 steady state, a ramping-core artifact indistinguishable in a log from a slow machine. Same discipline as reading `threads=` back out of the library: a precondition that is not checked is a precondition that drifts. §5 rule 5, amended 2026-08-16, generalises the *instrument* here without loosening the discipline: the governor is what establishes a stable clock on a host with a readable `cpufreq`, which is every host this ruling was made about, and a virtualized guest — which has no `cpufreq` directory at all — establishes it from `BenchmarkPeak` instead.
- **On an issue-bound host the P3 denominator is `min(same-host OpenBLAS, roofline × measured peak)`** (same ruling; cause is #17/#18, `docs/toolchain-notes.md` T12). OpenBLAS on Skylake-X is hand assembly whose K-loop folds accumulation and an embedded broadcast into single FMAs — instructions the intrinsic layer provably cannot emit — so it lives *above* the front-end ceiling that caps keel's kernels. Asking keel for ≥60% of that is asking the decode stage, not the kernel, and P2 already adjudicated that root cause rather than leaving it as keel's defect. So keel is asked for ≥60% of what its instruction stream *as-lowered* can express. Four properties keep this from being a dispensation:
  - **It only ever lowers the denominator, and only for a host that independently demonstrated a front-end ceiling** by the P2 classifier (ceiling mixes converging within 10% over a ≥25% mix spread, the shape under test not exceeding the ceiling it sets). FMA-bound hosts are untouched: vesta and antares face the plain, unmodified criterion, so at least one host measures the comparison with no assistance at all.
  - **The roofline is the one belonging to the shape `Sgemm` actually ran**, read from the `keel-bench-kern` marker of the very run that produced the ratio, and it carries P2's anti-vacuity shape guard unchanged: a shape more than 5% above the sweep's best zero-spill insns/FMA is refused a roofline outright and the host reverts to the plain OpenBLAS denominator. A fatter kernel cannot buy itself a lower bar — which is not hypothetical here: the guard refused the then-dispatched 4×32 (6.250 insns/FMA against the then-4.438 sweep best) while only the 2×32 the sentinel gated (4.625) was inside it — and the 2026-08-18 correction of that constant to 4.625 changes neither verdict, since 6.250 is outside `4.625 × 1.05` too, and that red is what surfaced issue #24. Dispatch was shipping a shape janus demonstrably should not run, and the guard declined to paper over it with a forgiving roofline; the fix was the dispatch bug, not the guard, and the next bullet is the ruling.
  - **It ratchets exactly as P2's floor does.** The roofline term is `maxᵢ p_i / I`, monotone in the gated shape's instruction count, so every improvement to the lowering raises it; when it rises above same-host OpenBLAS the `min` picks OpenBLAS and the amendment retires itself with no expiry clause to remember. Same standing task as §4/P2: when a toolchain lowers `MulAdd` to a 231-shaped FMA with a folded broadcast, re-audit and re-measure janus, which then reverts to the plain reference.
  - **Both ratios are always printed**, amended and plain, on every host. The gate's leniency is itself a number with a denominator; hiding the unassisted figure would be the reporting failure §7 rule 7 exists to prevent.
- **Microkernel shape is selected per host, by the same issue-bound/FMA-bound classification** (amended 2026-08-11, ruling on issue #24). P2 shipped two zero-spill shapes and `KERNEL.md` §7 measured the winner flipping between them: 4×32 on Zen 4 and Zen 5, 2×32 on Skylake-X by 11 percentage points. Dispatch took the registry's first entry, so it ran 4×32 everywhere — a performance bug on one of three hosts, and the one the roofline guard then refused. So `Sgemm` now classifies the host and picks the shape extremal on that class's binding cost: an FMA-bound host takes the fewest memory ops per FMA (4×32, 0.75), an issue-bound host the fewest instructions per FMA (2×32, 4.625). This is not a weakening; per-target microkernel shapes are what BLIS and OpenBLAS both carry, "one shape everywhere" was never a principle here, and P2's own data proved the physics — on janus the two shapes' throughputs stand in the inverse ratio of their instruction counts. Three properties keep it honest, and `KERNEL.md` §8 is the record:
  - **The gate requires that the shape measured is the shape dispatch selects.** The throughput sentinel judges the dispatched shape rather than whichever shipped shape measures fastest — with a per-host choice those stopped being the same claim — and the other shapes become its ceiling set. Both are benchmarked in one invocation, so "did dispatch pick the faster one" is answered from the same measurement: if a passed-over shape's lower bound clears the dispatched shape's point estimate, the gate fails. The blocked `Sgemm` at 2048³ is then re-measured with `KEEL_KERN_CLASS` pinned to the other class, as a cross-check on the number the criterion actually rests on.
  - **The classification is a proxy, so it is checked against measurement on every host, every run.** `archsimd` reports CPU features and never a vendor, family or model, and `internal/cpu` discards the CPUID signature word, so no microarchitecture is readable from pure Go here (`docs/toolchain-notes.md` T14, issue #25). `kern.HostClass` fingerprints the generation from a feature bundle instead — AVX-512 with VBMI2+VPOPCNTDQ is Ice Lake / Zen 4 or later — and the library prints its verdict and its grounds so the gate can compare them against the class its own convergence test derives from the measurements. Disagreement is a gate failure. Neither error direction can make a gate lenient: a wrongly-FMA-bound host dispatches the fat shape, which the roofline guard then refuses, making the bar *stricter*; a wrongly-issue-bound host gives up throughput, which the same-invocation shape comparison catches.
  - **The instruction counts the ranking reads are re-derived from the object code.** `Kernel.InsnsPerFMA` is a measurement recorded in Go source, and it decides what ships, so the gate recounts every shipped shape's loop body in the spill audit and fails on disagreement. An unaudited shape is unrankable rather than lean, which is a second lock on the spilling reference tile never being selected.
- **One re-run for a failing sentinel reading, and the retry is part of the record** (added 2026-08-11 by ruling, recorded on issue #4; this is an allowance granted to the gate model, not one the implementer may grant itself). A *throughput sentinel* criterion — P2's ≥55% floor, its P3 successor requiring ≥90% of the dispatched shape's roofline on an issue-bound host, and **P5's per-host scaling bars** (`CEIL_FRACTION`, `STRSM_FLOOR` in `scripts/gate-p5.sh`; named here explicitly, ruled 2026-08-19 on issue #6, because a future reader will not find a scaling margin inside a clause that lists only the two throughput floors — and repointed from the retired `SCALE_FLOOR` on 2026-08-20 by the §4/P5 amendment below, which is the whole reason a clause names identifiers instead of gesturing at "the scaling floor") — that reads as failing triggers exactly one immediate re-run; the criterion fails only if **both** runs fail. **Both outputs are archived in the gate record either way** (the session-end comment on the phase umbrella issue, pasted verbatim per `CLAUDE.md`), so a gate that passed on the second reading visibly says that it did, and a run of retries would be legible as one. This is a statistical allowance, not a mulligan: one retry, never a loop, and **never applicable to a correctness criterion** — oracle sweeps, differential tests, spill/call/BCE audits and the shape-agreement checks fail on first miss, because a differential test that passes on retry has found a nondeterminism worth more attention than the gate colour, not less.
  - It exists because janus's roofline attainment is the tightest margin in the gate and the only criterion whose ordinary variance can straddle its bar: two independent runs an hour apart read 95.0% and 93.7% against ≥90%. Writing that down converts a future fire drill into a documented allowance; leaving it as an operator's instinct is how "re-run once" decays into "re-run until green".
  - `scripts/gate-p3.sh` itself is unchanged and still fails on the first miss — the allowance is the operator's, and the archive is what keeps it honest. A gate that retried internally would have to be trusted to report that it had; a human re-run that must paste both outputs into the umbrella issue is auditable by construction. The friction is the feature: the allowance costs one deliberate act every time it is exercised, and this criterion is the last one in the project that should be optimized for convenience.
  - **A repeat at the same precision votes; a repeat at higher precision supersedes** (ratified 2026-08-19, ruling on issue #6). The allowance above says the criterion fails only if **both** runs fail, and the remedy the P4 ratio criterion orders for an undecidable reading — *"the remedy for `unmeasured` is precision, never a wider judgment"* — is *"a higher `-count` for this criterion on that host"* — two rules that look like they contradict each other and do not, because they answer different questions. A second run at the **same** `KEEL_BENCH_COUNT` is another draw from the same distribution: letting the better draw win is cherry-picking, so both-must-fail is the honest aggregation. A run at a **higher** count is not another draw but a *tighter estimator of the same quantity*, strictly more informative than the one it replaces, so it **supersedes** rather than votes and the verdict comes from the escalated run alone. Both outputs are archived either way, exactly as above; what the record must show is which kind of repeat happened, because that is what says whether the second reading was counted or was allowed to overrule the first. Two limits, and they are the whole safeguard: a row that fails the floor *with* the tightened interval is a real shortfall — no second escalation, no floor edit — and escalation cannot move a *reported* interval that already reads `0%`, because that is the floor of benchstat's reporting resolution and not a zero width — T21, whose `± 0%` means "narrower than 0.5%". Where the reported CI is `0%` this remedy is therefore inert on the number the gate grades, and the reading is **more** likely undecidable rather than less: the rounding band it stands for can straddle the bar (issue #110, where it already did: one 7.0-bar verdict flipped on a 0.014% move in the point estimate). The chain of legitimacy is by citation, not by authorship: that P4 clause predates the run, `gate-p4.sh:652` already prints the remedy in these words (*"if this host is CHRONICALLY indeterminate here, raise KEEL_BENCH_COUNT for this criterion on this host"*), and `KEEL_BENCH_COUNT` already existed with a default of 10. That is #104's standard met by citation rather than by authorship: an amendment may import a standard that predates the run, and may not invent one after seeing the result.
  - **How often it is needed is itself the signal.** Each retry is compliant on its own, so "one per reading" alone would permit a criterion retried indefinitely. The interpretive rule: a sentinel that needs its retry often enough for the friction to hurt is not noisy — it is reporting that the margin is gone, and the response is to raise the throughput or re-derive the bar, never to keep spending the allowance. Because every exercise is archived verbatim in the umbrella issue, the frequency is legible in the record rather than something anyone has to remember.
- **A verdict cannot be more certain than the least certain link in its derivation chain, so the host classification is graded in three states** (ruled 2026-08-16, issue #86). The classification is not a result; it is an *input* that four criteria divide by. When the measurement cannot decide it, the class is **`indeterminate` for that run** and every criterion consuming it reports `UNMEASURED` naming one cause — "classification indeterminate this run" — rather than each inventing its own failure. That is §5 rule 6 applied one level up the chain: one cause, one label, and an absent measurement gets `unmeasured` and never a red attributed to something else — so no healthy numerator is judged against a denominator chosen by noise, and no log line dispatches the operator to repair a fingerprint that was right.
  - **What happened.** On 2026-08-15 (`build/gate-p3-under-p4-708ddbb-run1.log`, and the healthy re-run at the same commit beside it) janus's classify invocation read both microkernels low against the peak kernel measured in the same invocation. The ceiling spread crossed 1.10, so the convergence test returned `why=diverge`, the host reclassified fma-bound, and **four verdicts moved on that one link**: the class-agreement check failed and told the operator to fix `internal/kern.HostClass`'s fingerprint; the sentinel faced the flat 55% instead of 90% of its roofline and failed at 42.7% of peak; criterion 6b's denominator switched from `roofline 105.52` to `openblas 194.35`, turning 75.1% into 39.5%; and criterion 6's aggregate followed. Against a *fixed* denominator the same two readings differ by 1.3 points (39.5% vs 40.8% of plain OpenBLAS). The 35-point swing was the denominator, not the kernel.
  - **The straddle test goes on the class-selecting comparisons, not on the result boundaries.** Two comparisons select the class from measured fractions: the ceiling spread against `converge_max` (1.10) and attainment against 1.0 (the falsification test). Both now take interval ends — `bench_ratio_lo`/`bench_ratio_hi` from §5 rule 5, measured, never a symmetry assumption about the point estimate. Clear of the bar on either side with a clean reading keeps its two-state answer, including the genuine class-disagreement failure this gate is *supposed* to raise; an interval that spans the bar yields `indeterminate`. The result boundaries — attainment against the 90% roofline floor, best-of-peak against the flat 55% — are self-contained and **stay two-state**, with §4's one archived re-run. With zero-width intervals the three-way tests reduce exactly to the two-way ones they replace, which is why every control written before this amendment keeps its verdict — the 29 that predate it are unedited (`scripts/roofline-test.sh`, which held 43 fixtures when this was written — stated as of that amendment rather than as a running total, since a count labelled "now" in a design document is a figure that goes wrong by itself).
  - **And no verdict *less* certain than its derivation requires: an undecided comparison whose branches agree decides the class anyway** (added 2026-08-16, same issue, before the amendment's first green run). The law above has a second edge, and the first cut of the amendment implemented only one of them. When the ceiling spread's interval straddles `converge_max`, *both* readings of that straddle can still lead to the same class: converged means the ceiling exists and attainment above it **falsifies** it (fma-bound), and not converged means no ceiling was established at all (fma-bound). Neither branch reads `roof`, and the flat floor that then applies is the same expression in both — so withholding the class there would be an `UNMEASURED` the data settles, which is this same defect pointed the other way. Reported as `why=falsifiedanyway` and `why=samemixanyway`, with the straddling interval still printed, so the record says *could not decide this, did not need to*. Two properties make it a measurement rule rather than an escape hatch: the collapse is tested over the **whole** interval — `roof_hi = pmax_hi / I` is the highest ceiling the reading admits, and falsification must hold at every point of it, never at the midpoint — and it can only ever move a host from `indeterminate` to a class it was already going to get on both branches, never between classes. **Found by a real reading grazing the bar rather than by review:** on 2026-08-16 antares measured a spread interval of [1.077, 1.100] against the 1.10 bar while retiring at 162.2%–165.2% of the roofline that interval implies. One rounding step higher and a host falsifying its claimed ceiling by 62% would have been reported "classification indeterminate".
  - **The three-state renderings are exercised on purpose, because a branch in the certifying instrument that has never run is untested** (authorized 2026-08-16). On this fleet they are otherwise unreachable — janus's class-selecting interval is zero-width, so no value of the 1.10 bar can sit inside it, and antares's attainment is 162%, nowhere near 1 — so the synthetic input goes on the **measurement** side, not the threshold: `KEEL_INSTRUMENT_WIDEN_CI=<pct>` widens each ceiling-set mix's interval around its own point estimate, which reproduces the 2026-08-15 condition (a host reading noisily) rather than a bar nobody would ship. Every shipped threshold prints in the log unchanged, every verdict line carries a `[synthetic]` stamp, the run prints **neither GREEN nor RED** and exits 2, and the artifact lands at `build/instrument-exercise-*` and never on a `gate-pN-<rev>` path where a reference-hungry diff could pick it up (#78). Same discipline as the `fakessh` dead-host arm and the must-fail fixtures: an induced failure is legitimate exactly when the artifact cannot be mistaken for evidence. *(Correction, 2026-08-16: when this sentence was written in `1c3eaca` there was no `fakessh` in the tree. The comparison was to an intended mechanism, not an existing one, and it read as precedent for four commits. `scripts/fakessh` now exists with its own fixtures — the reference is made true rather than repointed, because a citation to a mechanism that does not exist is exactly what the citation lint was built for, appearing in prose the lint does not reach.)* *(Correction, 2026-08-19, grounds issue #110: **"janus's class-selecting interval is zero-width" is false, and it was never a measurement.** It read width 0 off a reported `± 0%`, which is the floor of benchstat's CSV reporting resolution — "narrower than 0.5%" — and not a zero width; that column decided a shipped P5 verdict on a rounding step, which is what makes this a substantive correction and not a wording one. The archive refutes the categorical form on the same host and the same comparison: `[1.014x, 1.034x]` around 1.026 in one archived run, non-zero width, in a run whose CIs did not happen to round to `0%`. What survives is the quantitative claim, and unlike the original it carries its denominator — 1.10 − 1.034 = **0.066** of margin against roughly **0.010** of quantization width, about six quanta — so `KEEL_INSTRUMENT_WIDEN_CI` is still needed to reach these renderings, for a measured reason rather than an impossibility one. Two things are deliberately not touched. The bounds themselves are now measured at full precision by `tools/benchci`, so the classifier's straddle test resolves where it previously could not; and the five other `zero-width` sites in `scripts/roofline.sh` and `scripts/roofline-test.sh` describe a **fixture given no bounds**, which the input format *defines* as zero-width — those are constructions, not readings, and correcting them would assert something false about a definition. §5 rule 15.)*
  - **The induction is environmental, never a knob in the judging code** (ruled 2026-08-16, on gate-p2's fleet-incomplete aggregate). Criterion 5b's PASS — *"every host that produced a judgeable throughput reading cleared its floor (N/M)"* — had only ever printed 3/3 on this fleet, so the rendering where a **green line credits a proper subset of the fleet** had never executed, and a host will be down someday: its first firing should not double as its first test. The mechanism is `scripts/fakessh` on `PATH` as `ssh`, refusing one host with ssh's own 255 and "No route to host" while the other two genuinely build, run and measure. The gate is unmodified and unaware; it finds the host unreachable through the same machinery a real outage would use. **A flag that told the gate to skip a host would have proven only that the flag works.** `KEEL_INSTRUMENT_EXERCISE` exists alongside it but is deliberately impotent — it stamps, banners, withholds the verdict and exits 2, and is read nowhere near a comparison, a threshold, a tally or a host list, so setting it on a healthy fleet reports a stamped 3/3. That the aggregate *cannot* be forged from a flag is itself worth having on the record. Full synthetic discipline as above; the run doubles as the fleet's first degraded-mode rehearsal. *(The PASS quoted above no longer exists: the exercise fired, printed `(2/2)`, and the reading of it produced the next bullet's ruling, which replaced that branch with `UNMEASURED`. The exercise's target moved with it — the sentence is kept in its original form because it is what the instrument was aimed at when it found the defect, and the second run is owed to the code that replaced it.)*
  - **A fleet aggregate cannot describe a partial fleet as a whole one: absence resolves to `UNMEASURED`, once, for every criterion that judges a fleet** (ruled 2026-08-16, issue #90). *"A PASS reading `(2/2)` over a three-host fleet is a message-level truth carrying a fleet-level assertion — the criterion's claim is about the fleet, and a fleet with an absent member hasn't measured that claim."* §5 rule 6 gives the absent measurement its one available verdict, and criterion 6's OpenBLAS aggregate already spoke this way, so the two were saying different things about the same silence: **two aggregates with different absence semantics is the divergent-copies defect relocated to the verdict layer.** Both now call one function, `fleet_coverage` in `scripts/roofline.sh` — renamed from `p3_coverage`, because the phase prefix was itself the invitation to grow a second copy. Three properties keep it a measurement rule:
    - **It is not a weakening, and P2 is the go/no-go, so that must be explicit.** `unmeasured()` sets `FAIL`, so `UNMEASURED` blocks green identically to `FAIL`; nothing red can become green through this. What changes is only that a partial fleet stops being *describable* as a whole one. Per-host PASSes stand as measured — only the aggregate refuses.
    - **The counters that formed the fraction were grown inside the survivor loop**, which is why no complete-fleet run could have caught it: every fraction they form is survivor-denominated, arithmetically true, and renders identically when nobody is missing. The fix is a denominator the loop cannot touch (the configured host count) plus a separate tally for each way a host can fail to be judged — a host the run could not classify is not a host that never answered, and one leftover count would hide which happened.
    - **The two callers feed it different shapes, so both are fixtured.** gate-p2 excludes an indeterminate host from its measured count where criterion 6 includes it, so the same fleet arrives as `3 2 2 0 1` from one and `3 3 2 0 1` from the other; asserting only one would leave the other verified by reading, which is how the two aggregates came to disagree in the first place. `scripts/roofline-test.sh` carries 70 fixtures now, and gate-p2's five aggregate renderings are additionally driven by extracting them from the gate's own bytes rather than retyping them.
  - **Why §4's re-run allowance is not the remedy here and stays where it is.** That allowance was priced for one verdict: one deliberate re-run, friction as the feature, archived both ways. A propagating *input* spends four verdicts per exercise, which is a different purchase than the one §4 authorized. So the allowance stays for self-contained sentinel reds, and derivation inputs get the straddle test instead. Re-measuring an `indeterminate` is not the allowance being spent — there is no verdict to overturn — and it is therefore uncapped; the §4 frequency clause's logic still applies in spirit, since a host chronically undecidable here is reporting that its intervals are too wide for this bar.
  - **It withholds PASSes too, which is what makes it a measurement rule rather than leniency.** An attainment interval reaching above 1.0 is undecided about whether the host has already beaten the ceiling it claims, and a host cannot be graded against a roofline it may have falsified. Control 23 in `roofline-test.sh` is that case: 98.7% attainment, which would sail past the 90% floor, reported `UNMEASURED`.
  - **The gate now prints the quantity it decided on.** `gate-p3.sh` discarded both the ceiling spread and the mix spread (`read -r ... _CSPREAD _MSPREAD`), so when the classification flipped, the number that flipped it was nowhere in the log and had to be bounded backwards out of the threshold — which is how the first reconstruction of this incident got the wrong link, blaming the 90% floor. Both spreads and the attainment interval now print per host per run, against the bar each is judged by — §5 rule 8's "publish the underlying pair beside the derived figure" clause, applied to a class instead of a percentage: the derived figure was the classification, and its underlying pair was in no log.

  - **The ratio criterion is graded in three states, not two** (ruled 2026-08-15, issue #67). The bar and the pass condition are unchanged: a host passes iff the ratio's conservative lower bound — numerator down by its CI, denominator up by its own, §5.5's methodology — is ≥85%. ### Phase 5 — Parallelism, dispatch, polish (≈1–2 sessions)
- Parallelize the MC (ic) loop over a bounded worker pool sized by `runtime.GOMAXPROCS(0)`; shared packed-B panel per NC iteration, per-worker packed-A buffers from a `sync.Pool`. No background threads, no state between calls.
- Runtime dispatch finalized, and **the chain is per level, not one chain for the library** (narrowed 2026-08-12 by ruling, issue #40): **Level 1 dispatches `avx512 → avx2 → scalar`**; **Level 3 (the GEMM microkernel and everything blocked around it) dispatches `avx512 → scalar`**. Overridable by env `KEEL_FORCE=scalar|avx2|avx512` for testing, where `avx2` acts as a *ceiling* at Level 3 rather than a panic, so a legitimate Level-1 configuration can still call `Sgemm`; `ActiveKernBackend` then reports `scalar`, so no marker can believe it measured an AVX2 SGEMM.
  - **Why Level 3 advertises two rungs and not three.** `internal/kern` has no AVX2 microkernel, so the middle rung of a three-rung Level-3 chain would be unmeasured — and unmeasurable on the machines this project has. No gate host is AVX2-only silicon, and `KEEL_FORCE=avx2` on an AVX-512 machine establishes *correctness* under forced narrowing, not *performance*: front-end and port behaviour on a part that has AVX-512 is not evidence about a part that does not. An advertised chain whose middle link no gate can back is a claim, not a measurement, and §7 rule 7 forbids exactly that shape of claim. Level 1 keeps its AVX2 path because it is measured and has been gated since P1.
  - **The AVX2 microkernel is deferred with its unblocking condition named, not dropped:** an AVX2-native evidentiary host (real silicon with no AVX-512, so the kernel can be *measured* rather than merely exercised). Debt with a trigger. Correctness of any future AVX2 kernel remains testable on existing hosts via `KEEL_FORCE`; only the performance claim needs the new machine.
- The package must compile and pass (scalar path) *without* `GOEXPERIMENT=simd` — build tags make the fast paths additive. This is what lets it exist on proper `go get` terms the day the experiment graduates.
- Scaling benchmark, README with honest numbers, `doc.go`.
- **Named input carried in from P3: close janus's retention gap (issue #26), don't regress the Zens** (added 2026-08-11). - **P5 is ordered internally: single-thread remediation, then the parallel loop nest, then the scaling gate** (added 2026-08-12 by ruling; sequences #26, #36, #37 and the deferred measurements on #21/#22 ahead of the parallelization). Race-clean is table stakes for a Go library, and `checkptr`-clean is what race-clean means for code holding `unsafe`; excluding the pointer checker would certify keel safe minus the instrument that checks. So keel takes the local workaround, and it lands **inside #22's edge-handling campaign** rather than as a point patch: **`checkptr`-cleanliness is an admissibility condition on #22's candidates, not a competitor in the measurement** — masked-partial is measured against zero-padded-panel among `checkptr`-clean implementations only, and a faster variant that fatals under the pointer checker is disqualified rather than ranked. Admissibility first, then speed.
- **Stage 3 gets an evidentiary `.metal` host, and the ≥6× floor is unchanged by it** (added 2026-08-12 by ruling, issue #12). - **The scaling floor binds by parallelism class, not by routine list** (added 2026-08-12 by ruling, on the question of whether P4's derived routines are judged or only `Sgemm`).
  - **`Sgemm`, `Ssyrk` and `Ssymm` are one class and the ≥6× floor binds all three.** They are GEMM-shaped nests over independent tiles with no cross-iteration dependence, so the same parallelization is available to each by construction. Judging only `Sgemm` would let a serialization bug in the triangular C-update masking hide behind "the derived routines are reported, not judged" — precisely the routine where a subtle dependence would be introduced, and precisely the measurement that would have caught it.
  - **`Strsm` is a different class, and its floor was deferred to a measurement.** Its diagonal solves impose a dependency chain the other three do not have, and the parallelism available to it depends on `side` and shape in ways theirs does not. Writing 6× on it then would be inventing a threshold without a model, which this project has refused five times. So P5 measures `Strsm`'s scaling, reports it beside the judged three, and states the parallelism model behind it — what fraction of the work at the gate's shape is rank-update versus diagonal solve. That measurement and that model set its floor, which **binds from the commit that records it forward**. The deferral was recorded on issue #37 so it was a debt with a name rather than a permanent exemption.
  - **`STRSM_FLOOR` = 7.0×, and the model the deferral asked for is FALSIFIED rather than restated** (ratified 2026-08-16 by ruling, issues #37 and #89). The measurement arrived nine times over: three `gate-p5` runs (`2ba1956`, `7572390`, `8954f6d`) × three µarchs, `n=4096`, `threads=8`, boost off both arms, **7.403–7.668× net of CI** — Zen 4 7.602/7.458/7.594, Skylake-X 7.498/7.403/7.415, Zen 5 7.668/7.580/7.523.
    - **The falsification.** The model this gate required is the work split it prints, `rank_update=0.98413 diag_solve=0.01587`. Read `diag_solve` as an Amdahl serial fraction — which is what "state the model behind the number" was asking for — and at p=8 it implies a hard ceiling of `1/(0.01587 + 0.98413/8)` = **7.2001×**. **All nine readings sit above it**; the lowest, Skylake-X at 7.403×, is **+2.82% above a number that was supposed to be unreachable.** A model whose ceiling the data clears is not a model in need of adjustment, it is a dead premise, and **the favourable direction makes it no less a falsification** — the point of §5 rule 7 is that a check which cannot come out badly proves nothing, and a *ceiling* that the data walks through has failed in exactly that way.
    - **What it means mechanically, which is a finding about the nest.** The solves are not serial in effect: they overlap the rank updates. `Trsm` splits its **right-hand sides** at the top, because its rank update is `MB×n×k` with `MB=64 < MC=144`, leaving the `ic` loop one iteration — so the split had to go elsewhere, and the diagonal solves ride it. The implied serial fractions from the nine readings, `s = (p/S − 1)/(p − 1)`, are **0.619–1.152%**, strictly *below* the 1.587% work share. That inequality is the arithmetic signature of solves that parallelize.
    - **The replacement model** is the per-`(jc, pc)` B-packing residue plus the makespan tail of the last unit claimed — #65's Amdahl term for this nest — measured at that 0.62–1.15% across three µarchs.
    - **7.0× is a regression bar, not a derived threshold, and the distinction is the ruling.** A floor *derived from* a ceiling the data refutes would be theatre; a floor set *below every observation* is margin, which is what the ≥6× floor is too. 7.0× sits **0.403× (5.76%) under the lowest of the nine** and above the 6.0× general floor, so `Strsm` stops being the routine with no threshold at all without the number pretending to a provenance it does not have. 7.4× is rejected as unshippable — it would leave Skylake-X 0.04% of headroom and flake on the next run. It binds under the **same boost-off methodology** as its siblings, so it is not comparable to the three boost-on runs in the record.
    - **The dead premise stays visibly dead.** The gate keeps requiring and printing the work split, because it is a true fact about the shape and the input to this falsification — but it now prints *in words* that the split is not a serial fraction, and reprints the ceiling it would imply beside the reading that clears it, recomputed from each run's own declared split. Reported, judged by nothing: a future reading landing *below* that ceiling would refute nothing, since it is the nine readings above it that killed the model.

## 5. Testing philosophy (for the whole project)

1. **Oracle-driven:** float64 reference for every routine; the tolerance helper is the only place epsilons live.
2. **Differential across backends:** avx512 vs avx2 vs scalar on identical inputs must agree within reassociation tolerance — catches shim bugs independent of the oracle.
3. **Adversarial shapes first-class:** every dimension in {0,1,MR−1,MR,MR+1,…}; strides > width; overlapping aliases where BLAS defines behavior.
4. **Benchmarks are tests:** perf gates run in CI-mode locally (`go test -run=NONE -bench=Gate`) and the gate script parses the numbers. A silent 2× regression should fail a gate, not await a human.
5. **Gate benchmark methodology** (revised 2026-08-11, decision on issue #14): `-count=10 -benchtime=1s`, **every** measuring host's clock established stable — asserted per host, at the start of the gate and again at the moment of measurement, never assumed and never satisfied by one host on behalf of another, because a criterion that can be met vicariously is not a criterion — aggregated by `benchstat` (pinned as a module tool, so the version is in the repo). The gate compares **medians**, and a threshold counts as cleared only if it is cleared **net of benchstat's reported confidence interval** — numerator down by its CI, denominator up by its own. A distribution too wide for benchstat to bound is a failure to measure, not a pass. `-benchtime=3x` remains acceptable for smoke runs that inform no gate. **Stability is established by whichever instrument the host actually has** (amended 2026-08-16, forced by the ruling to measure on AWS instances rather than desktop hardware). Where `cpufreq` is readable that instrument is the `performance` governor, unchanged and still asserted at both times. In a virtualized guest there is no `cpufreq` directory at all, and `/proc/cpuinfo`'s `cpu MHz` is present, plausible, and a fixed nominal constant regardless of what the core is doing, so it is **never** read: a harness sampling it would sample a literal and certify stability on every run forever, where the absent files at least fail closed. There the instrument is `BenchmarkPeak` sampled at the head, middle and tail of a sweep — a register-only FMA-saturation loop whose FLOPs/cycle is ISA-fixed, so its rate is a monotone function of effective clock with every other term held, and a declining series is throttling while a wide one is contention. **A decline is an ordering, and an ordering below the instrument's own resolution is not one** (amended 2026-08-20, ruling on #6). As it stood the test asked only `head > middle > tail`, so it decided on the sign of differences smaller than what it could resolve: on keel-gnr it refused two of four triples across a total spread of 0.14%, and a random triple is strictly decreasing one time in six, so roughly one refusal in four was arriving by chance — rank statistics on noise rather than a thermal event, and ordering fabricated from sub-quantum differences is fabricated. Two repairs. First, the series is judged on `sec/op` and never on `GFLOP/s`, because `testing`'s `prettyPrint` picks its decimals from a value's **magnitude** and not from the precision of the measurement (T26): below 999.95 a column gets four significant figures, above it every integer digit. Both columns of one row go through that same function, so at 245 GFLOP/s the rate is quantized to 0.1 — 0.041% relative, and a median of ten samples lands on a 0.05 multiple — while the same measurement's 102762 ns/op is quantized to 1 ns, 0.00097%. The rate and its reciprocal, one run, resolutions **42× apart**, and every decline this test ever reported was one quantum of the coarse one. `tools/benchci` then keeps the interval at full float64. Re-parsing a rounded display string is #110's defect (T21) one column over. Second, a step counts as a decline only where the two windows' intervals are **disjoint** in that direction — A's slowest still faster than B's fastest — and a monotone verdict needs both steps to clear it. The floor is `(1+cA)/(1−cB) − 1`, derived from the two windows' own intervals by the same run on the same host from the same samples, so this remains a section with no threshold to tune and nothing in it was chosen after meeting a fleet; a genuine droop clears any honest floor by construction, so only the phantoms die. The judgement is a pure function (`clock_series`, `scripts/bench.sh`) with six controls in `scripts/roofline-test.sh`, one of them replaying keel-gnr's refused triple from its archived full-precision samples. This adds no benchmark and no new bar: peak is already measured on every sweep as §4/P2's denominator, and "too wide for benchstat to bound is a failure to measure" above already refuses the wide case. It licenses no *absolute*-frequency claim, which would need the FMA-port count that §4's measured-peak ruling (#11) deliberately does without. Per rule 6, "no `cpufreq` interface at all" and "the file is present and unreadable" are different causes and may not share one verdict: the first is a guest, the second is a defect. **Placement is pinned, fleet-wide and never selectively** (adopted 2026-08-21, ruling on #6). Every judged invocation runs under a CPU affinity mask, and the ceiling arm under the identical one — a share whose numerator and denominator came from different placement methodologies is not a share. The grounds are four independent readings that the unpinned instrument was reporting the draw rather than the code: zen4's `Strsm` verdict went red at `5ec5fea` and green at `33de3b2` on unchanged code, noise moving one verdict in both directions; zen5's `Ssyrk` cleared a bar its own derivation set 2.6 points below every healthy row by 0.4 points, at ±5.0% where the ladder read ±0.90%; skx's `Strsm` cleared 7.0 at its median and failed net of CI; and criterion 9's 5% band is narrower than the run-to-run spread of the rows it judges. A verdict that flips on placement is a weather report, and the cure is structural rather than a wider band: a tighter estimator of the same quantity supersedes a looser one, so a red that turns green under pinning is this section operating correctly and is disclosed with both readings side by side rather than avoided. The transition campaign therefore runs **both** methodologies and archives both. **The claim is falsifiable and stated as a prediction** (rule 15): the pinned arm's intervals must narrow materially against the free arm's on the same rows, and if they do not, the adoption is refuted by its own transition run and reverts. **Two limitations inside the number, not beside it** (rule 12). The mask is eight distinct physical cores within one NUMA node, so the `threads=1` rows are pinned to a *node* and not to a core, and the ±0.11% a one-core probe read on skx's `Sgemm` — against ±14.6% for the same quantity unpinned — is not promised by this weaker mask. And the mask changes what `testing` appends to every benchmark name, because Go reports the affinity mask's width as `GOMAXPROCS`: rows carry `-8` where the free arm carried `-192` or `-72`, which `bench_stat` strips optionally and every site naming a row explicitly must be checked against. Rationale: P1's first ratios came from `-benchtime=3x -count=5` reduced by min-of-samples, whose raw samples spread by 3.08× inside a single backend; ten one-second runs collapse that to low single-digit percent, and "clear the bar net of CI" means no gate can go green on a lucky run. Mechanics live in `scripts/bench.sh`, shared by every gate so none can quietly deviate.
6. **A gate red for the wrong reason is as untrustworthy as a gate green for the wrong reason.** A gate's product is verdicts, and a verdict whose cause is misattributed corrupts the record in either colour: it is remembered as what it claimed to measure, and what it actually measured is never revisited. Therefore **every gate criterion that consumes benchmark output declares the benchmarks it will read and asserts a minimum row count for each of them before reading any of them** — `bench_expect` in `scripts/bench.sh` is where that is enforced, because `bench_stat` printing nothing is otherwise indistinguishable at every call site from a benchmark that ran and reported nothing under the unit asked for. An absent measurement has exactly one verdict available to it — *unmeasured* — never a silent pass and never a red attributed to something else. Two corollaries with teeth: causes that differ must produce distinguishable verdicts even *inside* "unmeasured" (no rows at all, fewer rows than `-count`, and rows without the unit have different causes and are reported separately); and an instrument that cannot discriminate fails rather than returns a value, so a candidate sweep whose distinct families all measure the same rate is broken by construction and says so instead of crowning a winner by list order. Ruling: `docs/rulings.md`, rule 6.

7. **A check that could not have come out otherwise is not evidence.** The standing order, in two questions: for every confirmation, name the result that would have falsified it; for every isolation, name the single variable that differs between the arms. "Nothing could have" and "two things differ" both mean the check is not yet a check. **Corollary for compiler forensics:** blame flows upstream through the pass pipeline, so a pass whose fingerprints are on the assembly may be operating correctly on the output of a pass that did nothing. Idle registers next to a clobber are not evidence of an allocation decision. Ruling: `docs/rulings.md`, rule 7 — the tautology trap and the unvaried control, one of each.

8. **A summary is a cache with no invalidation protocol.** Every derived figure — a percentage, a ratio, a delta — is recomputed from the log it came from at the moment it is written, never carried forward from a prose summary, an earlier message, or a previous draft of the same document. Two consequences: **the number and its arithmetic are produced in one step** (grep the log, let `awk` divide, print), and **the underlying pair is published beside the derived figure** so a reader can check the division without the log. **And recompute the same quantity, not merely from the same log** — this rule's own failure mode, and the more expensive of the two: it instructs distrust of the published figure and trust in the fresh recomputation, so recomputing a *different* quantity from the right log yields a well-formed number that disagrees with a correct publication, with the rule having pre-committed the writer to believing theirs. Therefore read the caption's *definition* of a figure before recomputing it; treat **aggregation as part of a quantity's definition** rather than a detail below it; and treat a disagreement with a published number as **a question, not a verdict** — the first hypothesis is that a different quantity was computed. This rule binds its own citations: figures quoted in a ruling are verified against the tree before they enter this document, and where they cannot be found the verified figure is used and the substitution is stated. Ruling: `docs/rulings.md`, rule 8.

9. **A citation is a claim about where the grounds are, and it is checked like any other claim.** Every gate cites this document for its authority, so a citation that lands on the wrong rule misdirects every reader who follows it while looking exactly like a correct one. Two instruments remain and they are not interchangeable. **Resolution** asks whether the citation lands: `scripts/citation-lint.sh` parses this document's actual structure and rejects a reference to a section or item that does not exist. **Mint-verification** asks whether it was ever right, and this one cannot be automated — it is a reading of the cited ordinal against the content the citing site actually invokes, so a baseline is audited once at the meaning level before it is frozen, with the audit's date and census recorded in `docs/citation-externals.txt` so a later reader knows the freeze rested on a reading rather than an assumption. **Pinning** — whether a citation has *moved* — was retired 2026-08-16, and the loss is stated rather than absorbed: a renumber is now caught by review, not by CI. **A pin certifies stability, never birth-correctness**, which is both why pinning was never sufficient and why retiring it was affordable. Three consequences. (a) *Argument identity adjudicates ordinals*: sites making the same argument vouch for each other's meaning even where their numbers disagree, and the rule bodies pick the winner rather than the majority. (b) *Two notations are legitimate and only one is preferred going forward*: new citations use the explicit `§5 rule 5`, because that form cannot be misread as a subsection this document does not have, while the `§X.Y` shorthand sites audited correct in the 2026-08-16 census stay byte-for-byte — rewriting a correct citation in the document the gates cite as grounds is churn dressed as rigour. (c) *A citation of a different document is not a defect in this one*: ten sites across nine declarations use this notation for `docs/spill-report.md` or for the BLIS paper's own §4.3, and they are **declared** in `docs/citation-externals.txt` rather than guessed at, each declaration carrying the number of sites it covers so an exemption cannot silently widen — declaring more than the tree has is a stale reference, fewer is an exemption that grew to cover a citation nobody read. A deliberate quotation of a bad citation is marked, never normalised, for the same reason a misreported figure is marked rather than restated (#79): the record of the defect is the point. Ruling: `docs/rulings.md`, rule 9.

10. **Agreement across N sites is one witness, not N.** Before counting corroboration, establish how many *independent derivations* a claim has: restatements written from each other agree by construction, so **cross-site agreement certifies propagation, never truth**, and a claim that has spread is easier to believe and no more likely to be right. Two consequences. (a) *A mechanism stated as a property of code* — "serial", "allocates", "not inlined", "called per row" — is settled by grepping the implementation and by `git log -S` for when it became true, never by reading a further restatement of it. (b) *A retraction is corrected at every site in the paragraph a reader would be misled by*, not in a footnote or a later entry, because the propagated copies are exactly what a future reader will find first. Ruling: `docs/rulings.md`, rule 10.

11. **An instrument's output overrules its author's claims about it.** Where a fixture, a probe or a gate disagrees with the prose that motivated it, the instrument adjudicates: it is run against that reasoning *before* the reasoning is published or the output used anywhere, and a claim its first run refutes is corrected at the claim — in the fixture's own comment — rather than defended beside it. Being wrong before publication is the cheap time to be wrong, and the instrument is what makes it cheap. This rule is about **adjudication and nothing else**; what an instrument cannot see is rule 12's subject, and neither may be cited for the other's job. Ruling: `docs/rulings.md`, rule 11.

12. **A coverage claim enumerates what it cannot see, as part of the claim.** A kill-rate, a pass count, a sweep's row count and a branch tally are each an assertion about a population, so the population's holes belong inside the number's statement and not in a footnote or an omission: **a mutation unkillable in principle, an arm no configuration can reach, a path the run never entered.** Three consequences. (a) *An uncounted survivor and a provably-invisible one are different facts and may not share a number* — the invisible one is documented at the test, with the reason it cannot fail, so a later reader does not "fix" the test to catch it. (b) *A hole disclosed is not a hole excused*: naming an unexercised path is the minimum, not the remedy, and the disclosure carries what would exercise it. (c) *A hole no future action can close goes inside the number and is never filed as a debt* (amended 2026-08-21) — a debt entry promises eventual payment, so filing an unpayable one reads as "known, scheduled" where the truth is "known, permanent". The test is to **name the future action that would remove the limitation**; where the data is archival, the host is gone or the run is finished, there is none, and the stated-within-the-figure form is then not merely the honest disclosure but the only one. A debt stays filed only where it is scoped to something a future action can actually reach, and a forward-looking instrument aimed at completed runs is the tell that it is not. Ruling: `docs/rulings.md`, rule 12.

13. **Two cost terms are comparable only at their rates.** A count is not a time, so an argument that orders two terms of a cost by their counts — flops against flops, elements against elements — is arithmetic wearing measurement's clothes, and it predicts a direction that only the rates can supply. Rule 7's flop-share-is-not-a-time-share, one level up: a *count* share is not a time share either. Two consequences. (a) *A term whose rate is unmeasured is the unknown one, not the smaller one* — the honest prediction is "which dominates is unmeasured", never the direction the counted term implies, because the countable half is the half an argument organises itself around. (b) *A constant whose optimum depends on another term's rate is tuned jointly with that term, once* — tune the pair, not the parameter, since tuning it at today's rate ships a value that must be re-reversed when the rate moves, and each flip demands its own judged evidence. Ruling: `docs/rulings.md`, rule 13.

14. **A defect's severity is a function of its deployment context, not its code.** A grading such as "latent, not active" is a claim about what consults the defective code and what rests on its output, so it can go from true to false with not one byte of the defect changing — which means **a severity is stated with the deployment facts it depends on**, or it is a verdict with a hidden premise. Two consequences. (a) *When a directive changes what a subsystem is for, its open defects are re-graded against the new role* — at the issue, with the dead premise named rather than silently outgrown, because the stale grading is what a future reader finds first and it reads as current. (b) *A verification plan is re-graded the same way*: "no host exists to drive this on" is a fact about the fleet and not about the test, so a fleet change reopens which arms can be driven live and which stay fixtured, and the log names which were which. Ruling: `docs/rulings.md`, rule 14.

15. **A conservativeness claim about an instrument is a testable claim, so direction-of-error is a measurement.** "This reading errs in the safe direction", "this correction can only tighten the bar", "this bound is pessimistic" — each names a *sign* on an instrument's error, and a sign is something the instrument can be run against and asked. Rule 11 says the instrument overrules its author; this is the case rule 11 is least often applied to, because a safe-direction claim feels like it needs no check: being conservative, it cannot be dangerous to believe. It can. Getting the sign wrong converts an unexamined reading into a *certified* one, and the certification is what stops anyone looking again — so the error is not merely undetected, it is protected. **Found by being wrong in exactly that shape** (ruled 2026-08-19, issue #110): T21 argued from the meaning of a `± 0%` reading that raising `-count` was inert on such a row and that this made the reading *less* likely to be undecidable. The sign was backwards — the rounding band a reported `0%` stands for can straddle the bar, so the reading is *more* likely undecidable — and the argument was published without once being run against the adjudicator it described. Two consequences. (a) *State the sign as a prediction, then drive the instrument at it* — the same discipline as rule 12's unkillable mutant: a direction nobody made the instrument exhibit is a hypothesis sitting inside a certificate. (b) *A correction whose sign is measured may then be relied on as a bound* — `tools/benchci -bandtop` prints "and only ever toward FAIL" because widening an interval provably cannot raise a floor-net-of-CI, and it prints the count of moved verdicts so the claim is checkable on every run rather than asserted once here. Ruling: `docs/rulings.md`, rule 15.

16. **A published reference is an estimator, never a draw.** A number published for a later run to be checked against — a README rate, a registered baseline, an archived denominator — is *by construction* an estimator of what the host does, so publishing one run's reading as that reference silently chooses the worst estimator available: sample size one. The check that consumes it then measures the reference draw's **altitude within its own spread** rather than any property of the code, and it does so with a sign that depends on nothing but luck — a high draw manufactures future reds exactly as a low draw manufactures future flattery, and the flattery is the half nobody re-opens. **Found in exactly that shape** (ruled 2026-08-21, issue #6): gate-p5's README re-measure convicted two zen4 rows, and both published values were the **maximum** of their six-run history on the same physical instance (`Ssymm/8T` 610.8 … **654.3**, `Strsm/1T` 35.66 … **37.61**), so a 5% band was spent on the reference's own bias and neither disagreement resolved at the intervals the two runs actually measured. Three consequences. (a) *The estimator is stated beside the figure*, in the same sentence, naming the aggregation and the runs it aggregates — rule 8 already makes aggregation part of a quantity's definition, and a reference is where that omission survives longest because the number is consumed by a script rather than read by a person. (b) *Repairing the estimator is not amending the criterion*: the band is untouched and the standard was always "today within X% of what this host does", so a max-of-history reference was never a faithful implementation of it — which also means the repair needs no predating standard, because it restores one. (c) *A correction that only acquits on the data in hand is a loosening, whatever its vocabulary* — the interval-aware variant of this same check was drafted, computed, and refused here on that ground alone: all four rows in question tie at their archived intervals, so it would have retired two reds and convicted nothing, and rigour that moves verdicts in one direction is rigour asserted rather than measured (rule 15's sign, one level up). Ruling: `docs/rulings.md`, rule 16.

17. **A criterion may not judge a host its reference artifact predates.** Every bar this project applies is made out of an artifact — a bar-derivation set, a published README row, an archived baseline — and a host admitted *after* that artifact was made is absent from it by chronology rather than by any property of its code. Convicting it for the absence measures its admission date. **Found in that shape** (ruled 2026-08-21, issue #6): `keel-skx` joined the fleet after `CEIL_FRACTION` was derived from nine rows on three other hosts and after the README rows those runs published, and gate-p5 rendered it red for having no README row — a row that is *born* from a judged run, so its first judged run could not have had one. The class is **BASELINE-REGISTERED**, and it is structural in four parts. (a) *Three states, decided from tracked state and never from a flag*: unregistered with no witness that this silicon was judged before is genuine newness, so the verdict is `BASELINE`, green-compatible, and the run emits the candidate reference formed from its own numbers; unregistered **with** a witness is not newness but an obligation someone did not land, so it is `FAIL` naming the unmet registration; registered is judged against its own bar, derivation printed. **The witness is a tracked index, `scripts/judged-runs.tsv`, and the first version of this clause got that wrong** (amended 2026-08-21, ruling on #6; defect #114). It said the witness was the run's own archive — *the run that renders `BASELINE` creates the prior log that forbids it next time* — which is elegant, needs no reviewed act, and is true only on the machine that has been running the gate: `build/` is gitignored, so on a fresh clone, on CI, or on a second operator's machine no host has ever been judged, every host is new forever, and BASELINE renews on every run. **A per-machine witness defeats single-shot exactly as thoroughly as the permanent exemption this class was built to kill, and more quietly, because it fails only for readers who are not the operator.** The tracked form trades automatic-and-invisible for reviewed-and-visible: the gate proposes a witness row beside the baseline row it spends, both land in one reviewed commit, and a session that lands neither leaves the host unregistered and re-renders `BASELINE` — which is the honest state and is printed as a debt on every run rather than absorbed. The index is keyed on the **CPU model**, not the hostname, matching the registry it is read beside: one key shared with the criterion that consumes it, and a hostname key would hand a renamed host a second exemption. (b) *The instrument proposes references and never writes them.* An instrument that mints the reference it will later judge against has certified itself, so the gate emits a fully formed candidate row to a scratch file and landing it is a reviewed commit act, exactly as every reference artifact before it was. A candidate emitted from a single run states so in its estimator column and is not landable as it stands, per rule 16. (c) *A registered baseline is immutable except by the two doors that already exist*: supersession by a tighter re-measure, or dated re-registration citing a named code change — which is how a host's baseline legitimately moves the day an optimisation lands, with the commit as its grounds. A per-host bar is the *same* margin constant subtracted from a different baseline, never a second threshold with a second justification; and the hosts that derived the fleet bar stay on it, since for them the artifact does not predate the admission — they are the artifact. (d) **A baseline belongs to the era of the instrument that measured it, and an instrument change opens (c)'s second door fleet-wide** (added 2026-08-21, ruling on #6). A baseline is a number an instrument produced, so when the instrument changes the number moves for reasons that are not the host's code, and judging a new-instrument reading against an old-instrument baseline books **the methodology delta as host drift** — the cross-denominator error this whole rule exists to prevent, arriving through the registry itself. (c) already licenses a dated re-registration citing a named change; an instrument change is a named change that applies to every host at once, so the transition is an **era boundary**: every host renders `BASELINE` for placement-sensitive quantities, entries land from the new instrument's medians with rule 16's estimator honestly stated, derived constants re-derive by the same formula over new-era inputs, and published rows regenerate. **Found in that shape**: `keel-skx`'s only two readings (`5ec5fea`, `33de3b2`) are single free-placement draws, and §5 rule 5 pinned placement fleet-wide the same day — so importing them as this era's baseline would have registered a methodology difference as skx's own number. The loophole guard, without which "new era" becomes exemption-renewal-by-tweak: **an era exists only via a dated §5 or §7 amendment plus a both-arms transition archive**, recorded per era in `scripts/measurement-eras.tsv`, and each host gets **exactly one `BASELINE` per era**. Operator convenience cannot mint one, and a ledger whose current era cites no amendment resolves to *nothing* rather than falling back to the era before it — a fallback would silently do the misattribution the clause forbids. The era before pinning is named `free-placement` retroactively and deliberately undated: it was not a concept while it ran, and inventing an opening date would be a provenance claim no artifact supports. Ruling: `docs/rulings.md`, rule 17.

## 7. Standing orders

Eight rules of engagement for anyone — human or agent — writing code in this repo. **Every ordinal below is frozen**: rules 2, 4, 7 and 8 are cited from outside this document (`README.md`, `bench/`, `internal/vec/`, `docs/`, and about twenty-five sites across `scripts/`). Renumbering is therefore not a formatting choice; add at the end or not at all. Since pinning was retired (§5 rule 9) nothing checks the freeze mechanically — `citation-lint.sh` would still resolve every citation after a renumber, silently, at the wrong rule. The freeze is a standing order held by review.

*Retitled 2026-08-16.* This section was headed "Claude Code kickoff prompt" and opened *"Paste below into a fresh CC session in an empty repo… It is self-contained; it does not assume this document is present."* Neither clause has been true for a long time: the repo is not empty, the prompt is inside the document it said it did not assume, and `CLAUDE.md` is what a session actually reads first. The framing is gone; the rules it wrapped are unchanged and stay here, because **here is where the gates cite them.** Where `CLAUDE.md` restates one of these, this is the authority and that is the operational reminder.

1. **Toolchain:** Go 1.27rc (or newest 1.26.x) with `GOEXPERIMENT=simd`. Verify with a smoke build before anything else. All Makefile targets must set the env var; the scalar path must additionally build on a stock toolchain without it.
2. **Never recall the simd API — read it.** Before writing or editing anything in `internal/vec`, run `go doc simd/archsimd`, `go doc simd` and read the sources under `$(go env GOROOT)/src/simd/`. The package is experimental and has had breaking renames between releases; any identifier you remember from training is presumptively wrong. Copy exact names from `go doc` output.
3. **Work the phases in order (P0–P5 in DESIGN.md). Each phase ends with its gate script under `scripts/gate-pN.sh` exiting 0.** Write the gate script at the *start* of the phase, then make it pass. Commit on every green gate with message `P<N>: <summary> [gate green]`. Never begin phase N+1 with a red gate.
4. **Phase 2 is a go/no-go, not a hurdle.** If the spill audit or the 55%-of-peak floor fails after the documented kernel-shaping steps and one tile-shrink, STOP. Write `docs/spill-report.md` containing the ssa.html evidence and the assembly excerpt, and end the session asking for a decision. Do not proceed to Phase 3, do not switch to assembly on your own initiative.
5. **The scalar shim is the spec.** Every op in `internal/vec` exists in scalar form first, with differential tests binding the vector backends to it. A vector op without a scalar twin and a differential test does not merge.
6. **Tolerances come from the helper, nowhere else.** One `tolerance(n int, scale float32) float32` function per the model in DESIGN.md §5. If a test needs a looser bound, change the model with a comment explaining the numerics, never the individual test.
7. **Honesty in benchmarks.** Every benchmark result you report includes: CPU model, the rate against the host's *measured* peak (§4/P2 — never a formula-derived one), and the OpenBLAS reference number from the same machine when the cgo dev-harness is available. If OpenBLAS is not installed, say so and report percent-of-measured-peak only. Never present a number without its denominator, and never present two denominators for the same quantity. Two additions dated 2026-08-21 (ruling on #6): a reported rate states its **placement methodology** — pinned or free — because §5 rule 5's mask is what decides whether a near-bar verdict is about the code, and a pinned figure compared against a free one is two denominators for one quantity in the dimension nobody was watching; and a number **published as a reference** for a later run to check itself against states its **estimator** in the same sentence, naming the aggregation and the runs aggregated, per §5 rule 16.
8. **When the toolchain surprises you** (missing intrinsic, unexpected lowering, compiler bug), document it in `docs/toolchain-notes.md` with a minimal repro before working around it. These notes are a deliverable — this project is partly a field report on `GOEXPERIMENT=simd`.
